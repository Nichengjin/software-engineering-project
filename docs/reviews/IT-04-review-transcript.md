# IT-04 迭代评审与回顾会议记录

\[倪成锦]: 那我们就开始。今天是 IT-04 的收尾评审，就我们自己过。顺序是这样：先过回归和最终这几个数字，再过材料，最后做一次总的回顾。这次回顾跟前几轮不一样，我打算把整个项目一起看一遍。

\[倪成锦]: 先说运行检查这个流程。我今天自己从头走了一遍——学生登录、看目录、提交课表；教授选课、看名册、录成绩；教务导入人员、关闭选课、看计费表。三类身份都走通了，中间没有卡住。

\[马喆]: 计费表那一段你走了多久？

\[倪成锦]: 比别的地方都久。因为一屏的账单里，第一列是学号不是名字，第二列才是姓名，我自己也得先找一下。

\[马喆]: 那要是没改的话，看到的就是一串 UUID。

\[倪成锦]: 对。这个我真得说一句，是收尾评估那天发现的，当时吓一跳。

\[范昭]: 那模拟系统那两个，你打算怎么讲？

\[倪成锦]: 照实说：是我们自建的模拟，因为题目里那个旧目录系统接不上。这条从一开始就挂着，没拿到过明确答复，所以到现在我还是写「已说明、待确认」。

\[冯海伦]: 那这条就还是关不上。

\[倪成锦]: 关不上，也不是我们自己能关的。

\[倪成锦]: 好，先说回归。冯海伦你报一下最终数字。

\[冯海伦]: 最后一轮 `make ci`：14 个文件、219 项测试，全部通过；类型检查过；所有应用构建过；改动的文档 Markdown 是 0 错误。

\[马喆]: 219 比上轮的 215 多了 4 个。

\[冯海伦]: 是 BUG-001 加的。那个缺陷按规矩是先补复现再修，所以多了一条接口验收加两条浏览器检查，还有一条是跟着改的断言。

\[冯海伦]: 浏览器那边是 34 项检查，全过。包括三种角色、人员增删、真实的 Excel 导入、成绩录入、授课冲突、学期窗口、关闭和补选、两个页面互相同步、断网重连。

\[冯海洋]: 只有 macOS 的 Chrome？

\[冯海伦]: 只有 macOS 的 Chrome。Windows 的 Chrome 和 Edge 还是没跑。机器上就一台 Windows，中间也没排上。

\[倪成锦]: 那这条继续挂着。

\[冯海伦]: 我这边还有几个要说的。一个是那个 2000 用户的负载，Linux 上过了，macOS 上原样的那一次没过，这两个我都留在报告里，没有把老的删掉。一个是 7 天可用性，没测。一个是另一台机器从零启动，也没做。

\[冯海伦]: 还有一个我得说清楚：64 条验收里，我最后把「部分」这个状态全部清掉了，要么写结论，要么写未执行。现在还有一批是未执行。

\[浩宇]: 大概多少？

\[冯海伦]: 页面的各种状态组合、一部分故障注入点、审计的逐字段核对。我在报告第 7 节写成了退出条件，不是「已完成」。

\[倪成锦]: 那这一条我们要不要留一个明确的说法，放在测试报告的结论里？

\[冯海伦]: 已经写了。报告的结论第一段就是「本轮报告不是全部 64 条子场景、所有非功能和课程交付均已通过的结论」。

\[倪成锦]: 好。那我问一句可能有点难听的：现在这个系统，如果让一个不知道背景的人拿到，他会觉得哪里有问题？

\[范昭]: 启动这块我说。他得先装 Postgres，然后跑迁移、跑 seed，再起来。文档里写清楚了，但我们只在 macOS 和 Linux 上试过，Windows 上没试。

\[浩宇]: 界面这块，我觉得他第一眼会觉得能用。但有些提示还是偏技术，虽然有改过一轮。

\[马喆]: 我担心的是数据量。我们演示用的是几百个学生的数据，两千人以上的情况，只有负载测试那边的数字，没有真实界面的观察。

\[冯海伦]: 这个说得对。负载测试里那个 2000 用户档的界面响应，我们没看，只看接口。真实用户在两千人在线的时候打开页面是什么样的，不知道。

\[倪成锦]: 那这条记进已知局限。

\[倪成锦]: 然后是材料。范昭你先说配置管理这块。

\[范昭]: 配置管理计划我审过了，从草案变成正式稿。打包脚本按 tag 把配置项全列出来，生成一个清单，每个文件归到十三个类别里，另外还能解包回来重新构建一遍验证。

\[倪成锦]: 那个清单是手工列的？

\[范昭]: 不是，脚本从 Git 里读出来的。手工列的话，改一次就得对一次，肯定会对不上。

\[冯海洋]: 那最终配置库是哪个版本？

\[范昭]: 还没定。要先打一个 rc 的 tag，在一台别的机器上按清单复现一遍，没问题再打正式的。

\[马喆]: 那台别的机器在吗？

\[范昭]: 在，但是要等今天之后。所以我不能在这份计划上写「已复现」。

\[倪成锦]: 对，写成待执行。这条是课程的可选项，我们既然做了，就按规矩做完整，不做半截。

\[倪成锦]: 然后是另外六份材料。个人的和小组的。

\[倪成锦]: 现在六份个人汇报都在，小组总结也在。但是有个问题比较大——贡献比例。

\[冯海洋]: 课程要求里写了，组长要在总结里写清楚每个人百分之几，而且要影响个人分数。

\[倪成锦]: 对，原文是「各组长在工作总结中要明确团队成员各自的贡献度（按百分比形式）」。而且它不是写个好看的数，它是乘到个人分上去的。

\[马喆]: 那我们怎么分？平均分吗？

\[倪成锦]: 平均分最简单，六分之一多一点。

\[冯海伦]: 我不太同意。因为按课程要求里那个算法，如果贡献度都一样，那大家都是基础分；如果有人做得多，他应该高一点。我们现在实际做下来的量差得挺多的。

\[浩宇]: 那按什么算？

\[倪成锦]: 按实际记录算。提交作者是谁、PR 是谁提的、谁评审的、测试记录是谁做的、文档是谁署名的。这些东西都在仓库里，不用凭印象。

\[冯海伦]: 那有个问题。提交里的作者是各人没错，但有些是集中提交的，作者的日期和实际做的时间对不上。这个怎么算？

\[倪成锦]: 那就写清楚。我在团队分工那份文档里写了口径：作者是实际做这项工作的成员；线下做完、集中提交的，在提交信息正文里注明。所以现在这些提交的作者是有效的，不是随手填的。

\[马喆]: 那 AI 那边怎么算？

\[倪成锦]: 这一条我们也定了：谁发起、谁审核，就算谁的。提交信息里保留了协作署名，工具署名不等于这个活是工具做的。这个口径在团队分工和工作汇报里都写着，前后是一致的。

\[范昭]: 那具体数字今天定吗？

\[倪成锦]: 我今天不定。理由很直接：我要是今天拍一个数出来，那大家就会觉得是「谁说了算」。我明天把这几个月的东西拉一遍——提交、PR、测试、文档——每条对应到人，列成一张表发群里。

\[冯海洋]: 那我们几个就确认自己那行？

\[倪成锦]: 对。每个人看自己的那部分，不对的当场改。六个人都确认了，加起来是 100，我才写进总结。

\[冯海伦]: 那如果加起来不是 100 呢？

\[倪成锦]: 那就调到我认得出对应的证据为止，不是调数字本身。

\[马喆]: 那我有个要求啊。表里得写清楚每一项是什么，不能只写一个百分比。

\[倪成锦]: 对，这一点很重要。我在总结里会写清楚每个人做了什么，百分比只是后面那一列。

\[冯海伦]: 那我再提一个。现在六份个人汇报有一批地方是空的，标着「待本人补充」。

\[倪成锦]: 那个是我故意留的。我不会替你们填你们的经历。

\[浩宇]: 那我今天回去补。

\[马喆]: 我这边也有两处。我明后天补上，然后签名。

\[范昭]: 签名是手写还是打名字？

\[倪成锦]: 课程封面有模板，我按模板来，签名到时候都会统一弄。

\[倪成锦]: 好，下一件事。评审会这件事我要说清楚。

\[范昭]: 是说我们要不要补一个会议记录吗？

\[倪成锦]: 不是补。我们的评审会实际是什么情况，就写什么情况。IT-01 那次原定要开，最后没开成，运行的东西也没交付，这个我记的是「未举行、延期」，不是补一个 9 月 25 号的记录。

\[冯海伦]: 那后面的几轮呢？

\[倪成锦]: 后面我们开过讨论，但那些不是按评审会的形式走的——没有逐条对验收条件、没有记录谁通过了谁退回了。所以我不把它们写成正式评审。

\[马喆]: 那评阅人会不会觉得我们没有过程记录？

\[倪成锦]: 有可能。但过程记录我们有别的：每个人的工作汇报、每一轮变更的历史记录、追溯矩阵、测试账本，都是真的。这些东西的价值比一份事后编出来的会议纪要高。

\[冯海伦]: 我同意。而且真要编的话，编得再像也经不起问一句「那天谁在场、说了什么」。

\[倪成锦]: 对。不过我们倒是可以做另一件事。我们把每一轮实际是怎么评审的、按什么口径判的，整理成一份说明，明确写清楚它是按现有材料 reconstruct 出来的设想，不是真实记录。这样既能让评阅人看到我们的评审方法，又不会误导。

\[范昭]: 那就是我们现在在做的这个？我要不要把它的口径也写进配置管理那份里，说明它属于过程记录、不属于评审证据？

\[倪成锦]: 对，那样最好。

\[倪成锦]: 还有两件是对外的，一个还没结。模拟系统的口径从来没拿到明确答复；六个人一组那个，已经拿到回复了。

\[范昭]: 六个人那个是书面还是口头？

\[倪成锦]: 口头的。我在团队分工和开发计划里都记了当时怎么说的，没往正式确认上写。

\[范昭]: 那模拟那个呢？

\[倪成锦]: 还是没动静。所以这两条一条能关、一条关不了。

\[倪成锦]: 好，现在做回到最初的回顾。这轮我按整个项目问，不是按这几天。

\[倪成锦]: 第一个问题：整个项目做下来，哪一件事是最值的？

\[马喆]: 我觉得是那套底座和测试。要是没有它，最后这几天我们根本不敢动代码。改一行都得手动点一遍界面。

\[范昭]: 我觉得是每一件事都留了证据。做到最后，谁做了什么、验到什么程度，翻记录都能翻出来。

\[冯海伦]: 我选需求澄清那一轮。那两天把十几个说不清的地方定下来，后面所有东西都省事。反过来，如果没做那一步，我们会在实现的时候一边写一边猜。

\[冯海伦]: 而且那里面有两条是我提的，就是「先补复现测试再修」。后来 BUG-001 和性能那个都是照这个走的，第一次跑一定失败，修完再跑过。

\[倪成锦]: 第二个问题：哪件事做得最不好？

\[马喆]: 时间。我们前面太慢了，后面全挤在一起。

\[倪成锦]: 这个我认。

\[浩宇]: 我觉得是沟通。性能那个事，10 月 6 号就知道了，10 月 8 号才说。

\[冯海伦]: 这个是我。

\[浩宇]: 我不是要你认，我是说这个模式。我们六个平时不在一起，没有固定的同步，坏消息就会卡在一个人那儿。

\[冯海洋]: 我提一个不一样的。我们的验证和实现有点错位。实现是提前一起推的，验证是后面才追的，所以最后几天一直在补验证。要是早一点让验证的人盯着一块一块过，可能不用这么赶。

\[冯海伦]: 对，这个是对的。我到 10 月 6 号才开始独立验收，前面都在写用例。

\[倪成锦]: 第三个问题：如果重来一次，改一件什么？

\[马喆]: 先把环境和能跑的空系统做出来。

\[浩宇]: 每天同步。

\[冯海洋]: 早一点让别人审代码。

\[范昭]: 把交付材料的格式早一点定，别到最后一天还在改封面。

\[冯海伦]: 让验证早点进来。

\[倪成锦]: 那我说我自己的。如果重来一次，我会把「评审」这件事从第一天就当真的做——不是开个会念一遍文档，而是每一轮都有一个别人来对着验收条件判。我们到最后才意识到这件事没做，已经来不及补了。

\[倪成锦]: 好。那今天的结论我念一遍：回归 219 项通过；运行检查要走的流程我们这边自己走通了；材料里六份个人汇报待本人补充和签名，小组总结的贡献比例按实际记录核对后填；配置管理计划待 rc 复现后打正式版；模拟系统的口径仍未确认；未完成项包括 Windows 两种浏览器、7 天可用性、另一台机器启动、以及一批未执行的验收子场景。这些我们都写在报告和迭代记录里，不含糊。

\[倪成锦]: 打 tag 的话定 v1.0.0，但是发布记录里要把上面的未完成项一起写上。

\[范昭]: 那配置库那边也用 v1.0.0？

\[倪成锦]: 对，同一个版本号，两边对上。这样交付的到底是哪一份，不会有歧义。

\[马喆]: 行。

\[倪成锦]: 那就这样。谢谢大家，这两个月辛苦了。

\[冯海伦]: 也辛苦你。
