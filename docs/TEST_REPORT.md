## 1. 结论及使用边界

已经实际执行业务集成、真实 Chrome 主流程、数据库故障回滚、真实 API 进程重启以及 500／2000 已认证用户负载。测试结果只适用于下述本机环境；**本轮报告不是“全部 64 AC 子场景、所有 NFR 和课程交付均已通过”的结论**。

500 用户档完成 5 分钟预热及 30 分钟稳态，89,666 次稳态交易全部成功，目录查询均在10秒内；最终注册及客户端预期一致。**2000用户档未通过**：成功且≤120秒为61,939／98,252（63.04%，要求≥80%）；目录成功且≤10秒为31,079／39,381（78.92%）。未用缩短压测、快速拒绝或只统计成功请求来代替原性能口径。

最终 `make ci` 12文件／207测试、strict类型检查与全部构建通过。功能回归通过不能覆盖2000用户档的实测失败；该档的校验快照无超容量、无每生超过四门、课表与数据库注册集合一致，但806名学生与客户端最后确认注册不符。后续发现旧脚本未在取快照前等待服务端排空，不能将其当作最终静止状态，见第5.1节。

Windows Chrome／Edge、独立机器复现、七天可用性仍需补测；原矩阵尚未覆盖的子场景逐行保留，不回填“通过”。US-018 保持“进行中”。测试代码与本报告已经 [PR #24](https://github.com/Nichengjin/software-engineering-project/pull/24) 合入 main，PR 检查及合入后 [远程 CI](https://github.com/Nichengjin/software-engineering-project/actions/runs/37588458377) 通过；尚未发布。

### 5.1 2000用户失败复现与分层诊断（2026-10-06晚间）

SQL直接核实数据库为本机 `127.0.0.1:5432` 的 PostgreSQL 15.14；开发库 `wylie`、管理连接 `wylie_test`，实测仍仅使用随机新建库。PG连接上限100，`statement_timeout`／`lock_timeout`均为0；应用Prisma事务另有30秒时限，客户端HTTP另有120秒时限。**`CLIENT_TIMEOUT`表示客户端等待HTTP响应到期，不等于数据库连接超时。**

串行重跑两次2000用户，各预热30秒、测量180秒，保留5—15秒思考时间、原业务比例、120秒客户端期限及原第二档种子1001806；第二次仅增加预热期内20秒均匀启动。稳态资源样本均为2000个活跃用户。本轮未同时启动构建、浏览器或其他项目测试，但没有关闭机器上其他应用。

| 诊断指标 | 同时启动 | 20秒分批启动 |
| --- | --- | --- |
| 稳态成功且≤120秒／全部交易 | 3735／19016（19.64%） | 3876／18522（20.93%） |
| 稳态错误 | 13977连接错误、1282客户端超时、22旧版本 | 13417连接错误、1228客户端超时、1目录不可用 |
| 目录同步排队p50／最大 | 190.22／214.21秒 | 248.75／257.97秒（客户端排空时快照） |
| 事务连接及锁等待p95／最大 | 246ms／4.95秒 | 932ms／16.18秒 |
| PG活动采样的最大连接数 | 24，多数空闲 | 24，多数空闲 |

阶段诊断包含预热、测量及客户端等待结束，不与稳态交易分母混用；探针有额外开销。两轮均失败退出1，原始文件为 `.amp/in/artifacts/load-2000-diagnostic.{json,log}`、`load-2000-ramped-diagnostic.{json,log}`。这是**短时原因诊断，不是新的30分钟容量验收**，也不能与下午不同环境、不同测量时长的63.04%直接比较。

定位结果：

- **HTTP连接阶段存在本机突发接入限制。** 第二轮所有记录到的网络异常底层均为 `ECONNRESET`、系统调用 `connect`，发生在收到HTTP响应前。无数据库对照使用原生Node HTTP和Hono各自仅返回 `{ok:true}`：2000请求同时建连，两者均128成功／1872连接重置；分散在2秒内发出，两者均2000成功。与本机 `kern.ipc.somaxconn=128` 一致，说明不能把这些错误归因于PG。对照数据见 `.amp/in/artifacts/http-no-db-control.json`。
- **120秒超时主要积压在应用目录同步队列。** `CatalogService.fresh` 按学期串行，保存／提交先等该队列，再进入业务事务；首轮队列峰值1573个未完成调用，等待可达214秒，事务连接及锁等待最大4.95秒。队列等待不占用该业务事务的数据库连接；不存在“这批请求各自在PG里执行了120秒”的证据。分批启动仍失败，不能仅靠启动节奏修正就宣布性能问题解决。
- **同进程／同机资源仍是限制。** API、模拟服务、压测发起及响应解析共用一个Node进程；两轮事件循环延迟p99分别356／405ms。复测期间磁盘可用空间从约4.3降至2.1GiB，交换空间占用约13668MiB。已定位失败所在层及串行路径，但尚未用独立进程／独立压测机区分各部分CPU、内存与调度贡献，不直接认定真实部署的容量上限，也不增大超时或修改系统参数掩盖失败。

此外确认测试工具的终态校验顺序有误：第二轮客户端结束时仍有742个 `fresh` 调用未完成，原脚本先读取注册快照，随后才在清理中等待服务端排空。因此原806名、第二轮323名客户端差异都是当时快照，不能作为数据损坏或最终一致性结论。脚本现已先停止后台轮询并等待已准入业务完成，再校验数据库；客户端超时仍留在失败分母，不会追记为成功。

该工具修正做了先失败后通过的定向复测：40用户、20ms故意超时，修正前校验时仍有206个目录同步调用；修正后目录／事务活动数均为0，160条有效注册及课表集合一致，负载仍按预期失败退出1。证据为 `.amp/in/artifacts/load-drain-before`／`load-drain-after` 的JSON和日志。修正未追溯覆盖原始报告，完整2000用户终态与客户端重同步仍需重新验收。

修正后正常工具自检1416次交易全部成功，最终校验通过、诊断阶段无未完成调用；证据 `.amp/in/artifacts/load-diagnostic-positive.{json,log}`。strict类型检查及完整 `npm test` 再次通过：12文件／207测试，132.87秒，日志 `.amp/in/artifacts/load-diagnostic-regression-tests.log`；文档、仓库卫生、Action固定SHA检查通过。所有本轮随机数据库已清理，产品代码及依赖版本未修改。
