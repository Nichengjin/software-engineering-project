前端负责表达选择、保存编辑副本、展示有效注册及错误反馈；后端负责会话认证、角色与所有权、先修条件、时间窗口、容量竞争和事务一致性。页面禁用按钮不能替代服务端校验，学生页面成果也不能算作本人完成了后端选课算法。PR #11、#16 已集中合入 main，但这不证明本人参与创建、审批或独立验收。

## 二、学生领域阶段成果

登录公共层通过同源 `/api` 请求访问服务，cookie 使用 `credentials: include`，写请求携带内存中的 CSRF token；会话、密码和 token 不写入 localStorage。登录恢复读取 `/auth/me`，首次改密完成前不进入业务页面，退出走真实接口，401 会触发身份失效处理。这些机制供学生、教授、教务三角色共用，而不只是学生登录表单。

学生选课页同时读取课程目录、课表和变更通知。主选与备选分开编排，备选可调整优先级；额满班次仍可备选，已有注册的主选不会仅因额满被禁止保留。页面区分“本地选择”“已保存选择”和“有效注册”，明确保存不占名额、移除本地选择不立即退选。首次提交检查 4 主选＋2 备选，后续提交检查 1—4 主选与 0—2 备选；保存、正式提交和删除分别发出不同请求并携带原始 `expectedVersion`，提交及删除需要确认。

成绩单页面请求上一已完成学期，展示课程号、班次、成绩及历史导入／教授录入来源，区分未录入、无成绩记录和无已完成学期。关闭选课不等于学期完成，这一提示避免把当前学期误当作历史成绩。上述实现见[学生页面](../../../apps/web/src/routes/student.tsx)，交互约束见[前端说明](../../FRONTEND.md)。

## 三、两项可核实的技术难点

第一项是轮询与本地编辑之间的一致性。若直接用服务器数据覆盖输入，未保存选择会丢失；若把旧输入重标为新版本，又可能绕过冲突提示。现有 `useVersionedDraft` 保留 dirty 副本和原版本，服务器更高版本到达时阻断保存／提交，展示服务器选择，只有用户确认才采用新副本。成功写入后，迟到的低版本或同版本不同数据不会回滚已确认副本。[版本测试](../../../apps/web/src/lib/hooks.test.ts)对这些情况作出独立断言。这是代码与测试支持的设计难点，并非声称本人曾遭遇数据丢失事故。

第二项是写请求失败与结果未知的处理。409 不自动重发，业务错误保留本地输入；网络断开时不能把“没收到响应”当作“服务端没有执行”。[请求层](../../../apps/web/src/lib/api.ts)提示先刷新查询、不要重复提交，页面在写入结束后刷新资源，只有收到成功响应才接受新版本。资源轮询保持单批在途、卸载取消、失败保留最后成功数据并显示连接异常，避免慢请求不断叠加。现有测试和浏览器记录支持这些保护，但不能据此宣称全部超时重同步问题已解决。
