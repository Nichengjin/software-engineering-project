## 总体判断

六份个人报告都有相似的文风问题：技术内容比较充分，但常常先解释系统应当怎样工作，再列接口、字段和测试，读者需要自己拼出这一阶段为什么会这样做。个人经历又被放在章末补充，前面的说明与后面的经历重复出现。开头、测试、协作、图注和结尾还反复解释成果归属及验证范围，打断了具体问题的叙述。

各稿已经有足够的材料支撑改写。现阶段可以先把有关联的例子、判断和结果放到一起，再压缩重复的规格说明。日期也已经不少，尤其浩宇稿有明确的联调和验证日期；仅增加时间标记，解决不了过程不连贯的问题。

个人报告仍按课程要求覆盖需求、分析、设计、实现、测试和总结，但各人的篇幅应围绕职责有所侧重。同一件联调问题可以出现在几份报告中：学生端写页面如何处理，后端写事务怎样保证，测试写怎样发现差异。每份都照搬同一套完整机制，会掩盖个人工作的重点。

## 一、倪成锦：把后来补上的经历放回事情发生的位置

[原稿](nichengjin/report.md)中，1.5、2.4、3.5、7.6、8.4 节保存了很有用的实际经历。例如原来希望保存占名额，后来改变想法；看顺序图时不理解分析类术语；性能失败时先怀疑合盖和数据库，再依据记录改变判断。它们应当成为各章的叙述起点和转折。

目前的问题是，1.2 节先完整说明保存规则，1.5 节才补上本人怎样改变想法；第七章先讲完诊断，7.6 节又从本人视角讲一遍。建议把这些内容合在一起，按当时的问题推进，删去重复的规则解释。前面的“阶段任务”也可以缩成必要背景，详细字段与算法引用设计文档。

需要同步的内容有两处：8.3 节仍称“本份 v0.2”，与页首 v0.3 不一致；开头产物表写 OOA v0.3，后文已包含 v0.4 的图例修改。如果表格保留，应说明 v0.3 是当时分析阶段的产物，或改为当前汇总版本，避免两种时间口径混在一起。

组长稿可以侧重四次判断与协调：怎样确定规则、怎样选择技术和读懂模型、怎样根据性能结果继续修改、怎样调整成员接手安排。这样也能与小组报告完整介绍各模块的写法拉开侧重。本人已经回答过的经历可直接使用；尚无答案的具体意见和个人投入，不需要补成故事。

## 二、浩宇：围绕学生正在编辑的一份课表展开

[原稿](haoyu/report.md)第五章是最适合展开的部分。5.1 节有 v51 与 v52 的双页面例子，5.2 节有写入成功返回 v8、旧读取随后返回 v7 的顺序，5.3 节接着说明网络失败后为什么需要重新查询。这几种情况都与学生手上正在编辑的课表有关，可以连续讲清楚。

目前正文较早进入 cookie、CSRF、请求封装等公共层说明，随后又反复说明单元测试、页面夹具和真实联调分别能证明什么。建议先从保存与提交的区别写起，接到多页面和刷新问题，再介绍为此采用的版本处理。公共层保留与这些操作有关的内容，其他机制简述并引用原文档。

版本例子已有设计和测试依据，可以继续用条件句说明。实际发现并修正的弹窗焦点问题则按故障过程写。不要把两页竞态的设计例子改成某位真实学生已经丢失数据的经历。截图能看见本地与服务器的版本差异，禁用按钮的检查来自浏览器断言，图注应分别表述。

9.1 节的截图说明包含很长的启动环境、采集工具和重拍原因，读者还没看到页面解决了什么问题，就先读了一段执行记录。正文图注保留操作、可见结果和采集日期，复现细节集中到附件说明。最后集中说明尚需检查的超时重读和跨环境操作即可。

## 三、马喆：让授课安排和录分过程各讲清一个问题

[原稿](mazhe/report.md)已经有两个清楚的场景。2.2 节中教授原来负责 A、B，想改为 A、C，但 C 已被别人选择，因此失败后仍保留 A、B。5.3 节中十格成绩有合法值、错误值和空白，需要分别给出结果。这些例子比前面的字段定义更容易说明设计理由。

改写时可以先交代教授怎样选择授课，再追问取消和新增是否一起成功，由此引出一次确认整份安排；接着讲教授打开名册、填写成绩、看到部分成功以后如何继续改。后端的事务步骤和 DTO 只保留对结果有影响的部分。这样需求、设计和页面反馈能够接在同一条操作过程中。

第七章授课历史的时间错误有明确的失败和修复记录，应保留。它发生于团队集中回归，叙述可从“合入前的回归发现……”开始，再解释教授模块受到的影响，无需反复插入成果归属声明，也不必补出个人最先发现的情节。

第三章标题是面向对象分析，却配了 D02c 数据设计图，其中包含实现阶段的数据结构。建议将图移到详细设计章，分析章先用教授、授课资格、班次和成绩之间的业务关系说明问题。图本身可以继续使用，图注简要标明共享设计模型来源。

## 四、冯海洋：把教务员看到的影响和处理结果放在前面

[原稿](fenghaiyang/report.md)第三、四、七章的材料足够形成具体过程：教务预览学生休学时有三门课，确认前又出现第四门；导入名单中有成功、重复和缺字段的行；一个没有选课历史的人员却因为登录日志删不掉。

其中 3.1 节的例子刚解释完风险，就插入“不是声称实际发生过的一次事故”，读者的注意力被拉离设计问题。保持“假设……如果……”即可自然说明这是设计情境。3.2 节再解释如何核对刚才的预览，不必先铺开 token 中的字段。

导入部分可从一张有三类结果的名单展开：为什么已有人员跳过而不覆盖，错误行怎样保留行号，教务修正后如何再次导入。文件大小和压缩包限制可以合并成短段。第七章的删除故障和关闭等待提示保留实际失败、原因、处理与结果，避免与第二章重复介绍同一条数据库关系。

需求部分还有一个值得展开的区别：停用账号、修改人员状态和删除人员分别影响什么。用同一名学生在三种操作后的登录、当前课表和历史成绩说明，会比连续列限制容易理解。截图的长段采集说明也应压缩，与浩宇稿采用同一做法。

## 五、冯海伦：突出怎样得到可信的测试结论

[原稿](fenghailun/report.md)的过程材料较多，适合直接组织成几次测试方法的调整：用独立金额样本检查漏算和错算；控制两个学生先后进入处理，检查最后一个名额；重启测试在目录初始化完成前取快照，导致误报；负载测试在后端尚未处理结束时比较终态，得到仍在变化的数据。

这些经历已经能说明测试者怎样选择输入、确定预期、解释失败和修改测试准备。当前大量验收编号、完整账本及环境限制夹在其中，建议保留三个主要案例，其他覆盖情况用一张摘要表指向测试报告。性能章侧重负载怎样安排、成功怎样统计、何时取数；目录刷新实现的三轮修改简述结果并引用组长稿。

有一处内容需要纠正：7.1 节称倪成锦在需求问卷第 28 题“确认这些数字由原题写定，不属于小组可以重新解释的范围”。但倪成锦稿 1.5、6.4 节记载的是最初考虑自行定标或下调要求，之后最终仍采用原题指标。这里应分清最初回答、后续讨论和最终执行，不能把最终决定提前放进最初问卷。

108、134、207、215 是不同阶段的完整回归数量，73 项验收集成包含在相应集合中，32 项浏览器检查又是另一类记录。现稿已有范围说明，改写时可用一张时间表集中保留，避免每节重复提醒，也避免相加。冯海伦本人尚需独立复核的状态在结尾明确一次即可。

## 六、范昭：用接通、故障和重新启动串起外部系统

[原稿](fanzhao/report.md)的技术信息很完整，主要困难是 outbox、IN_FLIGHT、租约、版本、持久化等机制接连出现，读者还没弄清哪一步会失败，就要先理解状态名称。

### 为什么小标题读起来不自然

上一轮把正文的过程叙述方式过度用于目录，很多标题成了完整的提问、结论或操作提醒。例如“接收次数和最终金额分别检查”直接告诉读者怎么检查，却没有点出本节讨论的账单幂等性、重启恢复和金额一致性。“分别”强调了写作动作，对目录检索没有帮助。

主要有四个问题：

1. **标题承担了正文的解释。** “写入已经成功，先前发出的读取却晚到了”包含事件顺序，适合做段落开头；目录更需要“异步响应乱序处理”这样的主题。
2. **主语依赖上下文。** “失败提示出现以后，还要看留下了什么”没有说明是哪项业务、核对什么数据；单看目录无法判断内容。
3. **同一级标题的概括程度不一致。** 有的是一条检查动作，有的是完整业务领域，有的是个人反思，读者难以判断相邻章节的关系。
4. **问题句使用过密。** 少量“为什么”能引出真实故障，但每节都问“怎样／为什么”会使整篇像访谈提纲；“要／不能／分别检查”又使部分标题像提醒清单。

调整时用“具体对象＋本节侧重”的短语，保留必要业务名词。也不要全部缩成“需求分析／系统实现／问题解决”，否则丢掉了本节的具体内容。标题点出主题，正文首段说明发生了什么、为何要处理。
