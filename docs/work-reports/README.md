## 本人修改与团队汇总

每份报告先说明责任范围，再依据文件、提交和测试记录描述领域成果。既有候选主要由 Agent 集中协作形成，Git Author、分支名、PR 合入和分工表不能单独证明本人开发、测试或审批。初稿没有替成员编写未提供的个人经历，也没有预分贡献百分比。

1. 本人逐段确认职责与成果，删除不适用的内容，补充实际发起、设计、审核、修改、测试或沟通的部分。只有亲自完成且可核实的工作才改写为“我完成了”。
2. 搜索 `【待本人补充】`，加入真实时间、具体输入／预期／实际结果、遇到的问题、处理与回归、个人收获、尚未完成事项；可附提交、评审或脱敏记录。没有执行的工作保留未参与／未测状态。
3. 不把技术设计难点直接改写为亲历缺陷；不把全项目回归数量当作个人测试量。原 macOS 失败与后续 Linux 通过分别保留，环境差异和未覆盖项不能删去。
4. 六人完成个人修订后，组长核对小组总结中的 `【待团队补充】` 和 `【待团队确认】`，以真实工作记录确认贡献比例，六人合计100%；再补齐组号、封面和签名。
5. 最终统一材料格式并核对程序运行检查结果。初稿形成不等于课程验收、正式提交或发布完成。

## 每份文档的附件放在自己的目录

各人后续在自己的报告目录创建 `attachments/`；全组图表或签字材料放 `team/attachments/`。本轮没有必需截图，不创建空附件或不存在的图片引用。

例如，浩宇实际补充一张版本冲突截图后，可使用文件名 `20261008-student-version-conflict.png`，在报告中写相对引用 `attachments/20261008-student-version-conflict.png`，附拍摄日期、被测版本、环境、输入及结果说明。截图只展示实际状态，不作为未执行测试的替代证据。

附件须隐藏密码、token、完整SSN及真实个人数据；不要上传 `.env`、私有凭据文件、数据库转储或未脱敏日志。体积大的录像等材料先确认保存与分享方式，不直接堆入仓库。
