## 怎么写：把项目怎样做出来讲清楚

2026-10-09组长通读后指出，v0.2各稿读起来像规格说明书加审计声明，看不出系统是怎样一步步做出来的。之后的修订围绕具体问题、考虑依据、实际处理和结果展开。小组总结第三章已获认可，其余章节也已完成重写；个人稿可参考这一写法，按各自职责选择重点。

1. **让问题和决定接得上。** 交代为什么要处理这个问题，考虑过哪些做法，最后怎样选择；有后续失败和改主意的过程就继续写。各节根据材料展开，避免每节都套同一套四段标题。
2. **个人稿用“我”，小组稿用“我们”。** 已确认的日期、参与者和实际操作可以直接写。无需每段都加日期或原话；人机协作只在协作部分简述一次，技术正文集中讲业务和处理过程。
3. **先用例子解释，再引入术语。** 例如学生已经选上物理课，又保存了一份改成美术课的课表，接着说明两份数据为何要分开。编号放在引用中；outbox、版本号等确有必要的名词，在解释具体作用后引入。
4. **已知限制放在合适的位置。** 测试结果保留影响结论的环境与统计口径，尚未完成的工作集中到最后。删去反复的归属声明和“本稿不补造”等写作说明。
5. **按内容选择段落、表格和小标题。** 过程用段落，分工、数字与方案对照可用表格。小标题直接指出本节的问题，不重复“阶段任务／决策问题／处理与验证”。
6. **图放在它能解释问题的地方。** 选用已有UML图和实际截图，在相关段落附近说明看哪里、说明什么；不为凑每章一图而添加装饰。图注写操作与可见结果，长篇环境和采集细节放到附件记录。
7. **合理补足因果，具体经历以已知材料为准。** 用户已允许根据上下文补足解释和衔接，不在正文插入推断或待补标记。没有记录的具体谈话、工时、个人发现经过和新测试结果不补写；确实需要本人回答的问题集中整理，随后再放回对应章节。

每份报告从成员负责领域出发，依据需求、设计、源码、提交和测试记录展开工作过程。2026-10-08用户确认代码由成员与Agent协作完成、决策均由人类负责；Amp名称主要来自统一撰写提交信息。2026-10-09组长进一步澄清：总体设计在组内讨论过，实现阶段由成员监督Agent工作。报告采用这一协作事实，不把工具署名解释为成员未参与，也不把未提供的具体经历、独立验收或审批补成事实。

1. 本人逐段确认职责、技术叙述与成果，补充实际发起、设计、审核、修改、测试或沟通的具体内容，并按上面“怎么写”一节改成过程叙述。
2. 参考[个人稿审读意见](individual-style-review.md)，先重组已有案例、判断和结果；旧稿中的 `【待本人补充】` 集中整理为问题，已回答的内容写回相应章节。
3. 不把技术设计难点直接改写为亲历缺陷；不把全项目回归数量当作个人测试量。原 macOS 失败与后续 Linux 通过分别保留，环境差异和未覆盖项不能删去。

## 每份文档的附件放在自己的目录

各人在自己的报告目录维护 `attachments/`；全组图表或签字材料放 `team/attachments/`。2026-10-09按浏览器可见画面（1440×900）重拍了原整页或截偏的截图：倪成锦的保存无注册、正式提交、冲突保留旧注册（两张）、关闭与计费送达，以及浩宇图1、马喆成绩录入和冯海洋导入结果；浩宇的旧草稿保护图画面完整，保留10-06原图。环境、前置数据与断言见各报告截图一节；共享UML图使用相对引用，不重复复制源模型。

历史截图的采集日期与本轮整理日期分别标注，页面上的固定业务时间不当作拍摄时间。新增图片只引用实际存在的文件，注明被测环境、输入和结果；截图与测试断言配合说明场景，不替代未执行的验证。

附件须隐藏密码、token、完整SSN及真实个人数据；不要上传 `.env`、私有凭据文件、数据库转储或未脱敏日志。体积大的录像等材料先确认保存与分享方式，不直接堆入仓库。
