# 质量评分

用这份文档按产品区域和架构层次记录当前质量水位，方便持续知道最薄弱的地方在哪。建议每个迭代回顾时更新一次。

## 建议的评分标准

- `A`：覆盖完整、行为稳定、文档清楚、运行风险低。
- `B`：整体可接受，但还有明确短板。
- `C`：能用，但需要针对性补强。
- `D`：脆弱、缺少规范，或很多行为尚未定义。

## 初始模板

| 区域 | 评分 | 原因 | 下一步 |
| --- | --- | --- | --- |
| 产品面 | D | 已有需求分析、用户故事和验收条件初稿，业务歧义尚待评审，未形成确认基线。 | 评审 `docs/REQUIREMENTS_ANALYSIS.md`，解决影响实现的待确认问题后选入迭代。 |
| 开发流程 | B | 迭代、待办、追溯、完成定义和 tag 发布已定义，但还没有真实迭代跑过。 | 跑完第一个迭代后按回顾结论修订 `docs/ITERATION_GUIDE.md`。 |
| 架构文档 | C | ADR-001 已记录真实技术栈，UML 模型、模块和接口等总体设计尚未完成。 | 根据已定技术栈补齐 `docs/ARCHITECTURE.md` 及 StarUML 模型。 |
| 测试 | D | 策略已定义，还没有接入项目自己的测试。 | 按 `docs/TESTING.md` 接入框架，先补一条最小 smoke path 并加进 `scripts/ci.sh`。 |
| 可观测性 | D | 还没有日志、指标、链路的约定。 | 明确本地和 CI 怎么访问观测数据。 |
| 安全 | C | 默认约束已经有了，但具体实现还没落地。 | 根据项目接入真实认证、密钥和依赖治理。 |
