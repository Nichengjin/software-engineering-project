敏捷过程的价值观与原则
n 个体和交互胜过过程和工具
  Individual and interaction over process and tools

   n 人是软件项目获得成功最为重要的因素。

   n 合作、沟通及交互能力比单纯的软件编程能力
     更为重要。
   n 合适的工具虽然重要，但不能过分夸大工具的
     作用。
   n 团队的构建（包括个体、交互等）要比项目环
     境（包括过程、工具）的构建更重要。

敏捷过程的价值观与原则
n 敏捷过程的12条基本原则
 1. 我们最优先要做的是通过尽早的、持续的交付有价值
    的软件来使客户满意。
 2. 即使到了开发的后期也欢迎改变需求。敏捷过程利用
    变化来为客户创造竞争优势。
 3. 经常性地交付可以工作的软件，交付的间隔可以从几
    周到几个月，交付的时间间隔越短越好。
 4. 在整个项目开发期间，业务人员和开发人员必须天天
    都在一起工作。
 5. 围绕被激励起来的个人来构建项目。给他们提供所需
    要的环境和支持，并且信任他们能够完成工作。

n 敏捷过程的12条基本原则（续）
 6. 在团队内部，最具有效果并且富有效率的传递信息的

 12. 每隔一段时间，团队会在如何才能更有效地工作方面
   进行反省，然后相应地对自己的行为进行调整。

DevOps
• 运维（Operation）⼯作：部署以及运⾏过程中的监控、
  异常处理、优化调整等
• 软件开发环节的快速迭代使得运维环节的效率和响应成
  为主要瓶颈
• DevOps将敏捷的精神延伸到运维阶段，包含贯穿软件开
  发和运维的⼀系列实践集合
• 倡导以⼀种安全、快速、持续的⽅式将代码变更部署到
  ⽣产环境中

 DevOps技术价值流与技术实践
• DevOps的技术价值流
 ü   将业务构想转化为向客户交付价值的、由技术驱动的服务所需要的流程
 ü   开发人员能快速地完成开发、集成、验证，并将代码更新部署到生产环
     境中，从而有效地将前置时间（从开发任务产生到交付相应的价值的这
     段时间）缩短到小时直至分钟级别
• DevOps的技术实践
 ü   实现价值从开发到运维的快速流动
 ü   建立从运维到开发的持续、快速的反馈机制
 ü   建立持续的实验和学习的企业文化
持续集成
• Continuous Integration，简称CI
• 持续集成实践
  ü   开发人员频繁地（一天多次）将代码变更提交合并到中央存储库，
      并自动运行构建和执行单元测试，从而确保新代码可以和原有代码
      正确地集成在一起
  ü   如果持续集成失败，开发团队就要停下手中的工作，立即修复它，
      直到持续集成成功

• 主要目标
  ü   使正在开发的软件始终处于可工作状态
  ü   更快地发现、定位和解决错误
  ü   提高软件质量，减少验证和发布新软件所需的时间
 持续交付
• Continuous Delivery，简称CD
• 任何代码变更提交后都能够
  ü   自动运行构建和执行单元测试
  ü   自动将所有代码变更部署到测试环境和类生产环境
  ü   确保当代码变更部署到生产环境后可以正常工作，从而以可持续的方
      式快速向客户交付新的代码变更
• 如果代码没有问题，可以继续手工部署到生产环境中
• 让正在开发的软件始终处于可部署状态同时实现快速交
  付，能够应对业务需求，并更快地实现软件价值
 持续部署
• Continuous Deployment，简称CD
• 任何代码变更提交后都能够
  ü 自动运行构建和执行单元测试
  ü 自动将所有代码变更部署到测试环境、类生产环境以及生
    产环境
• 实现从代码变更提交到生产环境部署的全流程自动化而
  无需人工干预
• 加快代码提交到功能部署的速度，并能快速地收集真实
  用户的反馈
