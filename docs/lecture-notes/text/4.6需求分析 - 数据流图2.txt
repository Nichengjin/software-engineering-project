父图和子图的平衡问题
父图和子图的平衡问题
局部文件问题


n 文件(数据存储)总是局部于分层数据流图的某一层或
 某几层,所以数据流图中引入的文件都是局部文件。
分解的深度和层次问题


n 一个加工的分解最好不要超过7（9）个子加工。超过七个
  时，可以用增加层次，减少子加工数的方法。
n 分解在逻辑上应合理、自然，不能硬性分割。也就是说，
  要根据问题的逻辑特性进行分解。
n 在保证数据流易理解的前提下，尽量减少分解层次。这样
  可以减少层次的界面。
n 分解要均匀。即在一张数据流图中，不要有这样的情况：
  有些加工已是基本加工，另一些加工还要分解好几层，但
  绝对均匀不可能，不要相差太大。
命名问题


n 数据流命名

 n 名字应代表整个数据流（有时也会把现实环境中传递的
  一组数据中最重要的那个数据的名字作为数据流的名字）
命名问题


n 数据流命名（续）

 n 现实环境中，传递的一些表格、单据的名字可以直接作
  为数据流的名字。
命名问题


n 数据流命名（续）

 n 不要使用空洞的、缺乏具体含义的名字。

 n 不要把控制流作为数据流。

 n 如果在为某个数据流命名时遇到困难，可能是数据流图
  分解不当，应考虑重新分解DFD。
命名问题


n 加工（处理）命名

 n 顶层的加工名可以是软件项目的名字。

 n 不要使用空洞的、缺乏具体含义的名字。

 n 通常先为数据流命名，然后再为与之相关联的处理命名。
   这样命名比较容易，而且体现了人类习惯的“由表及里”
   的思考过程。
 n 如果在为某个加工命名时遇到困难，可能是数据流图分
   解不当，应考虑重新分解DFD。
命名问题


n 加工（处理）命名（续）

 n 加工的名字最好由一个谓语动词加上一个宾语组成。如
   “计算运费”、“准备机票”。也可以把宾语和谓语动
   词颠倒书写。如“运费计算”、“机票准备”。
 n 名字应该反映整个处理的功能，而不是它的一部分功能。

 n 通常名字中仅包括一个动词，如果必须用两个动词才能
   描述整个处理的功能，则把这个处理再分解成两个处理
   可能更恰当些。
数据流图的用途


n 作为交流信息的工具

n 作为分析和设计的工具
 n 用数据流图辅助物理系统的设计时，以图中不同处理的定时要
  求为指南，能够在数据流图上画出许多组自动化边界，每组自
  动化边界可能意味着一个不同的物理系统，因此可以根据系统
  的逻辑模型考虑系统的物理实现。
n 可以从数据流图出发映射出软件结构

   这种划分自动化边界的方法暗示以批量方式更新库存清单
