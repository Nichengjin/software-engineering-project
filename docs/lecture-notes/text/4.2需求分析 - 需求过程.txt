什么是需求过程

n 需求过程是用来导出、确认和维护系统需求文档的
一组结构化活动。

n 通常，一个良好的需求过程应包括下列活动：
 n 需求提取

 n 需求分析和协商

 n 需求确认




             2
    需求提取（Requirement Elicitation）

n   需求提取是通过与客户、系统用户和其他与系统开发相关
    的人员交流来发现需求的过程；
n   必须从项目干系人的角度考虑问题，花时间找到他们的真
    正需求；
n   为提出系统需求，必须理解待解决问题、组织的业务过程、
    系统可能使用方式、系统的应用领域，以及文档中与系统
    相关的内容，并与项目相关人员讨论他们需要的系统服务
    和系统约束。

系统需求的资料来源
n   主要来源是新系统的各种系统相关者，即项目干系人
n   系统的用户。从两个方向来收集资料：
    u   水平方向：物流、人力流、资金流、信息流、单据流、报表流、数据流
    u   垂直方向：业务操作用户、管理用户、主管（决策）用户
n   客户
n   技术人员技术、维护方面的需求
n   从各类系统相关者中识别出关键的人做领域专家
n   其他来源

    访谈

n   准备问题的原则
    u   问题应该是循序渐进的，先一般后细节；
    u   所提问题不应该限制用户在回答过程中进行自由发挥。组织问
        题尽量客观公正；
    u   逐步提出的问题在汇总后应能反映应用问题或子问题的全貌，
        并覆盖用户对目标软件系统或其子系统在功能、行为、性能诸
        方面的要求。




                    6
    访谈

n   第一组问题（语境无关的问题）
    u   谁是这项工作的最初请求者？
    u   谁将使用该解决方案？
    u   成功的解决方案的经济收益是什么？
    u   存在另一个你需要的解决方案源吗？




                     7
    访谈
n   第二组问题（使分析员能获得对问题更好的理解，并使客户
    能够表达对解决方案的感觉）
    u   你将如何刻画将由某成功的解决方案产生的“好的”输出？
    u   该解决方案强调了什么问题？
    u   你能向我展示（或描述）解决方案将被使用的环境吗？
    u   存在将影响解决方案的特殊性能问题或约束吗？




                        8
    访谈

n   第三组问题（关注会谈的效率）
    u   你是回答这些问题的合适的人员吗？
    u   我的提问和你想解决的问题相关吗？
    u   我是否问了太多的问题？
    u   还有其他人员可以提供附加信息吗？
    u   还有其他我应该问你的任何问题吗？

简易的应用规格说明技术

n FAST: facilitated application specification technique

n 一种面向团队的需求收集法。这种方法提倡用户与
  开发者密切合作，共同标识问题，提出解决方案要
  素，商讨不同方案并指定基本需求。




                                                          12
简易的应用规格说明技术

n 初步访谈，通过用户对基本问题的回答，初步确定
  待解决的问题的范围和解决方案
n 开发者和用户分别写出“产品需求”，组织会议

n 会前准备：
 u   要求每位与会者在会议前列出对象、服务、约束条件
     （成本、规模、完成日期）和性能标准（速度、容量）
     列表




                                13
 简易的应用规格说明技术
n 会中讨论：
 u   是否需要这个新产品？
 u   每位与会者把他们在会前准备好的列表展示出来讨论，由协调人主
     持讨论这些列表，目标是针对每个议题 ( 对象、服务、约束和性能 )
     都创建出一张意见一致的列表
 u   一旦得出了意见一致的列表，就把与会者分成更小的小组，每个小
     组的工作目标是为每张列表中的项目制定小型规格说明，并讨论
 u   每个与会者都制定出产品的一整套确认标准，并把自己制定的标准
     提交会议讨论，以创建出意见一致的确认标准
n 会后：由一名或多名与会者根据会议成果起草完整的软件需求规格说
 明书

    FAST例子
n   假定一个为消费者产品公司工作的FAST团队已经被提供了
    下面的产品描述：
    我们的研究表明，家庭安全系统的市场正以每年40%的比率增
    长，我们希望进入该市场，试图建造基于微处理器的家庭安全
    系统，该系统将保护和/或识别一系列不希望的“情况”，如非
    法进入、火警、火灾或其他。该产品，暂时称为SafeHome，将
    使用合适的传感器来检测每种情况，可由房主编程，并且当情
    况被检测到时，自动地给监控机构拨打电话。


                   15
n   对象列表：
    u   若干烟雾检测器、若干窗和门传感器、若干运动检测器、一个警报器、一
        个事件（某传感器被激活）、一个控制面板、一个显示器、一组电话号码、
        一次电话拨号等。
n   服务列表：
    u   设置警报器、监控传感器、电话拨号、控制面板编程、读显示器。
n   开发约束列表：
    u   系统的制造成本必须低于80美元，必须是用户友好的，必须是和标准电话
        线接口的。
n   性能标准列表：
    u   传感器事件应该在一秒钟之内被识别，应该实现事件优先级模式。

    场景分析（use case）
n 一个use case是一个描述软件如何被用于给定情形的场景。
n 首先标识参与者——角色

n 然后定义use case

n use case回答的问题：
    u 该参与者完成的主要任务或功能是什么？
    u 该参与者将获取、生产或改变什么系统信息？

    u 该参与者是否必须通知系统关于外界环境的变化？

    u 该参与者希望从系统获得什么信息？

    u 该参与者是否希望被通知未预期的变化？


                     19
    SafeHome例子
n   对于SafeHome可以定义三个参与者：
    u   房主（用户）、
    u   传感器（附属于系统的设备）
    u   监控和响应子系统（监控SafeHome的中央站）
n   房主和产品以一系列不同方式交互：
    u   输入密码以允许所有其他交互
    u   查询安全区的状态
    u   查询传感器的状态
    u   在紧急情况时按下紧急按钮
    u   激活/关闭安全系统

                         20
    一个关于系统激活的用例如下
n   1.房主观察SafeHome控制面板的原型以确定系统已准备好接收输入。如
    果系统未准备好，房主必须物理地关闭窗户/门，以便“ready”指示灯
    出现（“not ready”指示灯意味着某传感器是开着的，即某门或窗户是
    开着的）。
n   2.房主使用键盘键入4位密码。将密码与存储在系统中的有效密码进行
    比较。如果密码不正确，控制面板将鸣叫一声并复位，等待再次输入。
    如果密码正确，控制面板等待进一步的动作。
n   3.房主选择键入“stay”或“away”以启动系统。“stay”只激活外部传
    感器（内部的运动监测传感器是关闭的），“away”激活所有传感器。
n   4.当处于激活状态时，房主可以观察到一个红色警报灯。

原型化方法

n 原型：向相关人员演示系统提供的功能
n 需求过程中两个阶段都可能使用原型技术

n 需求提取阶段的原型：针对难以理解、不好把握的需
  求
    u 原型化使需求的真正含义易于理解；
    u 原型化是开发用户接口的唯一有效方式；

    u 原型化有助于在投入高开发成本前确定系统的总体可行性和

      可用性；
    u 最终系统有时可以通过向原型添加和修改功能来开发。



                22
    原型化方法
n   三种原型化方法：
    u   纸上原型法：定义场景、画出界面
    u   Wizard of Oz：由人模拟系统
    u   可执行原型：选择适合开发原型的语言
n   需求提取阶段的原型系统通常不能反映系统性能、效率等方面指
    标，仅用于发现功能需求。
n   需求确认阶段的原型：能用于试验的系统原型
    u   确认原型必须比提取原型更完整
    u   检查是否满足客户、用户的实际需要
    u   可用于开发测试用例

                              23
    原型化方法

n   废弃型（快速原型）：起解释作用
n   进化型：最终演变为产品
n   原型可能要求投入较高成本，并可能导致延迟交付；
n   不提倡把原型做成最终系统：原型趋向于非结构化，会导
    致系统灵活性降低、长期成本增加、以至于系统生存期缩
    短。


                  24
    需求提取中注意的事项

n   确定系统的边界
n   从多个角度考察待解决的问题
    u   对确定需求优先级很有帮助：多个角度下都被建议的需求应该
        具有高优先级。
n   把需求按必要程度分三类：
    u   必须要满足的需求
    u   很想要但对系统目标不是必要的需求
    u   可能满足但也可能取消的需求

    需求分析与协商（Analysis & Negotiation）

n   发现一系列原始需求之后，应分析它们之间的冲突、重
    叠、遗漏和不一致。在具备了有效的分析信息之后，项
    目相关人员就可以协商得到一套认可的系统需求；
n   需求分析、协商与需求提取是不可分割、互相交错的两
    个过程；
n   经常，需求分析中会细化需求定义文档或开发系统模型，
    通过模型来揭示需求中更深层次的矛盾或不足。

需求提取、分析和协商的螺旋

    项目干系人与需求协商

n   协商主要是讨论需求冲突，找出每个人都满意的折衷方案；
n   除了逻辑与技术上的问题，组织与行政上的一些考虑也可
    能左右项目需求，所以必须与各方面项目干系人协商以做
    出需求决策：
    u   例如：新系统涉及到权力的丧失或转移




                    28
    需求分析原则

n   操作性原则
    u   必须理解并描述问题的信息域，建立数据模型；
    u   必须定义软件应完成的功能，建立功能模型；
    u   必须描述作为外部事件结果的软件行为，建立行为模型；
    u   必须对描述信息、功能和行为的模型进行分解，用层次的方式展
        示细节。




                    29
    需求分析原则

n   指导性原则
    u   在你开始建立分析模型前先理解问题
    u   开发使用户能够了解人机交互将如何发生的原型
    u   记录每个需求的起源及原因
    u   使用多个需求视图
    u   给需求赋予优先级
    u   努力删除歧义性


                       30
    在需求分析中使用需求分类

n   需求分类是发现需求之间的共性和例外关系的依据。冲突和
    重叠的需求最有可能发生在同一类需求中。有时某些类似需
    求可以合并。
n   需求分类可以提高文档跟踪能力。当某类需求变更时，应考
    虑同一类中其他需求是否受到影响。
n   需求分类可以帮助找到遗漏的需求。在正常分类下某一类里
    没有需求时，往往意味着遗漏了某些重要需求。

                31
    在需求分析中使用问题

n   每个需求是否和系统/产品的整体目标一致？
n   所有需求是否在合适的抽象层次上被规约？
n   需求是否真的必要或是它表示了一个对系统目标而言可能并不重
    要的附加特征？
n   是否每个需求被界定并且无歧义？
n   是否每个需求均有归属？
n   任意需求是否和其他需求冲突？
n   是否每个需求均在系统或产品驻留的技术环境中可达？
n   每个需求在实现后是否可测试？

                 32
    使用交互矩阵发现冲突与重叠

n   交互矩阵的各行和各列都对应一项需求，而每一个矩阵元素都用
    来表示对应的两个需求是否冲突、重叠或者独立；
n   可使用电子表格来做。行首和列首都标上需求编号或标识符，把
    每一项需求跟其他所有需求比较，对于需求冲突，填入1，对需
    求重叠填入1000，对需求独立填入0。最后对行或列求和，每项
    需求的总和除以1000的余数就是冲突数目，商数就是重叠数目；
n   大量的冲突和重叠表明，此项需求的任何更改都可能大大影响系
    统其他部分。


                  33
需求分析与协商中注意的事项

n 保证需求是可测试的
 u   摒除需求中不确定、不完整、不正确的部分
     • 例如：“要能立刻访问水质的信息”这样表述是不可测试的；
     • 应准确地描述：“要在请求后2秒内找到水质的记录”。
 u   确定每个副词和形容词的定量描述
 u   用特定实体的名称代替代词
 u   要确保在需求文档中定义了每个名词

                 34
    需求分析与协商中注意的事项
n   各种非功能需求规格说明可能使用的度量：
    u 可靠性：出错时间、错误发生率


    u   有效性：交互请求后出错的可能性
    u   性能：每秒处理事务数、用户输入的响应时间
    u   可用性：学习75％的用户功能所需要时间、在给定时间内，由
        用户引起的错误平均值
    u   健壮性：系统故障后重新启动的时间
    u   完整性：系统出错后，允许的数据丢失的最大限度

需求确认（Requirement Validation）

n   需求确认：目标是检查被定义的需求集合，并发现需求
    中可能存在的问题。最终要确保开发方与客户间没有误
    解、需求定义与规约间保持一致。
n   要检查的问题可能包括：
    u   缺乏与质量标准的一致性
    u   由匮乏的词语描述的需求具有不确定性
    u   在分析过程中没有发现的需求冲突

                      36
    需求确认（Requirement Validation）

n   必须明确需求分析和需求确认是不同阶段的任务，尽管它
    们有共同点：
     u 共同点：它们都要检查系统需求的完整性和一致性；
     u 需求分析所针对的是从有关方面提取的、未被转换过的需求，

       可能既不完全又不是结构化表达的；
     u 需求确认所针对的是包含全部系统需求的需求文档的最终草案。

       需求确认是需求文档业已完成，请求获得批准之前的一个检查
       步骤。



                     37
    需求确认（Requirement Validation）

n   需求过程是从问题空间向求解空间转化的第一步，所以需求确认
    没有任何东西可依靠，它只能增加双方的信心，但这也是在离开
    问题空间前确保需求能被相关人员接受的最后机会了；

n   发现并修复需求问题能节省后期返工的成本；

n   需求确认要花费一段时间：阅读文档、开评审会、原型试验……
    请做好思想准备：若不解决需求问题就开始系统开发，准备迎接
    某种程度的返工。


                     38
    需求评审

n   组织正式的需求评审：
    u   由一组人系统地检查需求、讨论问题的解决方案；
    u   评审组包括双方的人员代表，应由未参与需求过程的人主持；
    u   评审组成员最好具有各自不同方面的技能、知识、经验，以利
        于问题的发现；
    u   评审是为了发现并解决问题，而不是为了责备任何人。需求中
        的冲突应在评审中得到解决。


                    39
    需求评审
n   评审的内容：针对前面介绍的需求特性，检查每项需求
    u   审核项目目标；
    u   审核需求与目标相符与否；
    u   系统环境、系统功能、系统的限制等；
    u   对开发过程中或系统运行过程中存在的风险进行评估和记录。讨
        论和比较各种可选方案，并和客户就使用哪种方案达成一致意见；
    u   随着开发的进行（以及需求改变和增加时），怎样继续检验并确
        认需求？测试小组怎样测试已经正确实现了所有的需求？谁提供
        测试数据？
