软件过程
软件过程


n 软件过程是为了获得高质量软件所需要完成的一系列
 任务的框架，它规定了完成各项任务的工作步骤。

n ISO
   9000对过程的定义: 使用资源将输入转化为输出
 的活动所构成的系统。
A Team-Based Definition of Process


n A process defines Who is doing What, When, and
  How, in order to reach a certain goal.

瀑布模型
瀑布模型特点


n 阶段间具有顺序性和依赖性
 n 必须等前一阶段的工作完成之后，才能开始后一阶段的工
   作
 n 前一阶段的输出文档就是后一阶段的输入文档

n 推迟实现的观点
 n 清楚地区分逻辑设计与物理设计，尽可能推迟程序的物理
  实现
瀑布模型特点


n 质量保证的观点
 n 每个阶段都必须完成规定的文档，没有交出合格的文档就
   是没有完成该阶段的任务。
 n 每个阶段结束前都要对所完成的文档进行评审，以便尽早
   发现问题，改正错误。
瀑布模型优点


n 可强迫开发人员采用规范的方法（例如，结构化技术）

n 严格地规定了每个阶段必须提交的文档

n 要求每个阶段交出的所有产品都必须经过质量保证小
  组的仔细验证
n 瀑布模型的成功在很大程度上是由于它基本上是一种
  文档驱动的模型
瀑布模型缺点

n 要求用户不经过实践就提出完整准确的需求，在许多情况下
  都是不切实际的
n 仅仅通过写在纸上的静态的规格说明，很难全面正确地认识
  动态的软件产品
n 将本来非线性的软件开发过程人为地加以线性化，不符合实
  际中的软件开发情况
n 软件开发耗时长，可运行版本要等到项目后期才能得到，一
  旦在后期发现错误，付出的代价将是巨大的。
n “由文档驱动”的这个事实也是瀑布模型的一个主要缺点,
  这可能导致最终开发出的软件产品不能真正满足用户的需要
V模型
V模型


n 瀑布模型的改进，强调测试活动与分析和设计之间的
  关联：
  n 单元测试和集成测试－>校验程序设计；

  n 系统测试－>校验（verify）系统设计；

  n 验收测试－>确认（validate）需求；

n 与瀑布模型关注文档和工作产品不同，V模型的关注
  点是软件开发各阶段的活动以及正确性，因此V模型
  是以活动驱动的。
Tips：验证与确认


n 验证（Verification）
 n 目标是确定系统中各项功能可以正常工作，实质上是检查
   实现的质量如何。
n 确认（Validation）
 n 目标是确定系统实现了全部的需求，确保开发方建造的是
   正确的、用户需要的产品。
V模型的改良之处与存在的问题


n 本质是把瀑布模型中一些隐含的迭代过程明确出来，使开
  发活动和验证活动的相关性更加明显；
n V模型使抽象等级的概念也更明显：所有从需求到实现部
  分的活动关注的是建立更多的系统详细表述，而所有从实
  现到交付运行的活动关注的是对系统的验证和确认。
n 和瀑布模型一样，都是对软件开发过程过于简单、理想化
  的抽象，对需求变化的适应性差。
原型/快速原型模型


n 所谓原型，是一个可以实际运行的模型，它在功能上
  可以看作是最终产品的一个子集（展示了目标系统的
  关键功能）。

n 原型模型的优势：
 n 快速原型模型是不带反馈环的，软件产品的开发基本上是
  线性顺序进行的。
  n 原型系统已经通过与用户交互而得到验证
  n 开发人员通过建立原型系统已经学到了许多东西

 n 利用原型能统一客户和开发人员对软件项目需求的理解，
   有助于需求的定义和确认；
 n 可以考虑结合瀑布模型，二者互补性强。用快速原型做为
   需求分析的一种技术，用于收集客户的真实需求，然后把
   客户满意了的原型再作为瀑布模型的输入，从而达到优势
   互补。
原型/快速原型模型

n 使用原型必须要注意的问题：
 n 由于要求能够快速建立可供运行的模型，原型不可能像最
   终产品一样面面俱到；
 n 客户：不可把原型当作软件的正式运行版本；

 n 开发人员：同上。还必须牢记原型中没有考虑质量因素的
   部分；
 n 使用前要与用户达成一致：原型只是模型而已。
