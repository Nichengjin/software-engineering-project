微软过程（Microsoft Process, MP）
n Microsoft 公司自己独特的软件开发过程，综合了
 RUP和XP的许多优点，是对众多成功项目的开发经
 验的正确总结。
n MSF的过程模型来自两个方面：
 n 微软开发应用程序的过程；

 n 一些有效的、公认的过程模型；


n 详细论述参见《微软软件开发解决方案框架》（第
 二版），麦中凡、陶伟编著，北京航空航天大学出
 版社

                            2
微软过程术语
n   项目前景（vision）与项目范围（scope）
    n   项目前景是对项目要解决什么问题的开放性描述，它代表项目的
        远景目标
    n   项目范围描述的是在项目的限制条件内，需要完成哪些具体的目
        标，主要是指所有特定的近期目标
n   功能说明书
    n   阐释了软件每一个特性的功能和执行方式，以及所有特性的组合
        关系和整体架构
    n   单页：概要性的描述所有产品特性的功能、性能及其在项目中的
        优先级
    n   详细：从技术细节上详细描述如何实现所有的产品特性
n   程序经理
    n   职责是在规定的项目资源、期限等限制条件下，确保产品能够如
        期发布。                      3
微软过程的过程原则
n 项目计划应该兼顾未来的不确定因素

n 用有效的风险管理来减少不确定的因素的影响

n 经常生成过渡版本并快速地测试软件来提高产品的

 稳定性及可预测性
n 采用快速循环、递进的开发过程

n 用创造性的工作来平衡产品特性和产品成本

n 项目进度表应该具有较高的稳定性和权威性

n 使用小型项目组并发地完成开发工作，并设置多个
 同步点
                         4
微软过程的过程原则（续）
n 将大型项目分解成多个可管理的单元，以便更快地

 发布产品
n 用产品的前景目标和概要说明指导项目开发工作—

 —先基线化，后冻结
n 避免产品走形

n 使用原型验证概念，对项目进行早期论证

n 把零缺陷作为追求的目标

n 里程碑评审会强调改进工作，避免相互指责



                        5
微软过程的组队原则
n   小型的、多元化的项目组
n   角色依赖和职责共享
n   专深的技术水平和业务技能
n   以产品发布为中心
n   明确的目标
n   客户的主动参与
n   分享产品的前景
n   所有人都参与设计
n   认真从过去的项目中吸取经验
n   共同管理、共同决策
n   项目组成员在同一地点办公
n   大型项目组也像小型项目组一样运转
                       6
微软过程的特点——与AP、RUP比较
n   微软过程的生命周期
    n 每个生命周期发布一个递进的软件版本，各生命周期持续、
     快速地循环。
    n 每个生命周期分为五个阶段，
     n 构思阶段（Envisioning Phase）

     n 计划阶段（Planning Phase）

     n 开发阶段（Developing Phase）

     n 稳定阶段（Stabilizing Phase）

     n 部署阶段（Deploying Phase）

    n 每个阶段均涉及产品管理、程序管理、开发、测试、发布
     各角色及其活动，各阶段结束于一个重要里程碑。

n 构思阶段——前景/范围认可里程碑
 n 主要工作：

  n 确定产品目标

  n 完成对客户和市场的调研分析

  n 确定新版本产品应该具备的主要特性

  n 确定相对于前一版本而言，新版本应该解决的问题和需要增加的
   功能

  n 前景/范围说明书

  n 风险评估说明书

  n 项目组织结构说明书

微软软件生命周期
n 计划阶段——项目计划认可里程碑
 n 主要工作：
  n 根据产品目标编写系统的特性规格说明书，这份说明书主要描述
    软件特性、系统结构、各构件之间的相关性以及接口标准
  n 从系统高层开始着手进行系统设计
    n   描述整个系统的设计方案
    n 绘制系统结构图
    n 确定系统中存在的风险因素

    n 分析系统的可重用性

  n 划分出系统中的子系统，给出各个子系统和各个构件的规格说明

  n 根据产品特性规格说明书制定产品开发计划

 n 产品：
  n 功能说明书

  n 风险管理计划

  n 项目总体计划书和总体进度表               11

微软过程的人员
n 角色合并原则

 n 项目组内的开发人员不能兼任其他角色

 n 不要试图合并两个有明显利益冲突或制约关系的
  角色
         产品管理   程序管理   开发   测试   用户体验   发布管理
  产品管理           N     N    P     P      U
  程序管理    N            N    U     U      P
   开发     N      N          N     N      N
   测试      P     U     N          P      P
  用户体验     P     U     N    P            U
  发布管理    U      P     N    P     U
  其中：“N”表示不能合并，“U”表示不建议合并，“P”表示可以合并

微软过程的人员及组织特点
n 结合了 RUP 和 AP 的优点，做了进一步的深化

 和发展
 n 角色划分：提出了产品管理和程序管理这两种两权分立的

  角色；
 n 角色的相互地位和交互关系：各角色相互平等，交互的关
  键是交流和沟通；
 n 角色分配：角色合并原则

 n 项目组规模和人员配备与管理方式：由专家式行政管理和

  小型化、多元化项目组组队方式构成的矩阵结构。

微软过程总结
n 微软过程是一套比较完整的软件过程模式，它

针对商业环境下具有有限资源和时间约束的项
目提供了一套操作性很强的成功经验总结。

关于经典软件过程模型

n 上述经典软件过程模型仅是实际中使用的

 模型的一部分；
n 应根据客户、用户、开发人员所处环境及

 解决问题的需要来定义和剪裁过程模型；
n 对于可能需要从多个角度来关注的开发过

 程，不能局限于一种过程模型。
