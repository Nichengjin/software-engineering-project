软件体系结构
软件体系结构的发展历程


n “无体系结构”设计阶段
 n 计算机硬件向专用方向发展，科学与商业领域使用完
  全不同的机器硬件；
 n 虽然高级语言已经诞生，但开发主要采用汇编语言；

 n 此阶段系统规模较小，很少明确考虑软件体系结构，
  所以一般不存在软件系统的建模工作；




                             2
软件体系结构的发展历程

n 萌芽阶段
 n “软件工程”概念被提出，开展了有关过程、方法及

  支持工具的研究；
 n 结构化开发技术成为主流；

 n 软件工作的范围从只考虑程序的编写扩展到从定义、

  编码、测试到使用、维护等活动的整个软件生命周期；
 n 软件体系结构已经是系统开发中一个明确的概念：结

  构化程序中，模块的聚集和嵌套构成层层调用的高层
  结构；


                             3
软件体系结构的发展历程

n 初级阶段
 n 20世纪80年代初，面向对象开发技术逐渐兴起，成为
  研究热点；
 n 抽象数据类型和面向对象技术的出现使体系结构的研
  究逐渐得到重视：
   n 对象的封装降低了模块间的耦合，为构件层次上的软件重用提
   供了可能；
   n 类库的构造、分布式应用系统的设计等规模大、复杂度高的系
   统，也需要对体系结构进行研究；



                               4
软件体系结构的发展历程


n “高级”阶段
 n 20世纪90年代后，软件开发技术进入了基于构件的软件
  开发阶段；
 n 软件开发的中心是描述系统的高层抽象结构模型，程序
  开发模式也由“算法＋数据结构”向“构件开发＋基于
  体系结构的构件组装”转变；
 n 软件体系结构作为开发文档和工作产品开始出现在软件
  过程中，它也逐渐成为软件工程的重要研究领域。

软件体系结构风格（SA Styles）

n 软件体系结构风格根据软件系统的结构定
 义了软件系统族。它通过施加于构件上的
 限制及组成与设计规则来表现构件和构件
 间的关系。
n 体系结构风格为一个软件系统及怎样建造

 该系统的相关方法表示了一种特殊的基本
 结构。


                       12
软件体系结构风格（SA Styles）

n   Garlan和Shaw对通用体系结构风格的分类：
    ① 数据流风格：批处理序列；管道/过滤器；
    ② 调用/返回风格：主程序/子程序；面向对象
      风格；层次结构；
    ③ 独立构件风格：进程通讯；事件系统；
    ④ 虚拟机风格：解释器；基于规则的系统；
    ⑤ 仓库风格：数据库系统；黑板系统；

软件体系结构风格（SA Styles）

n   每种体系结构风格定义了：
    n   一组构件：完成系统所需的某种功能；
    n   一组连接件：实现构件间的“通信、协调和合
        作”；
    n   约束：定义构件如何被集成到一起形成系统；
    n   语义模型：使得设计者能够通过分析系统的构成
        成分的已知性质而理解系统的整体性质。



                            14
管道和过滤器风格

n   每个构件都有一组输入和输出，构件读输入的数
    据流，经过内部处理，然后产生输出数据流。这
    个过程通常通过对输入流的变换及增量计算来完
    成，所以在输入被完全消费之前，输出便产生了。
    因此，这里的构件被称为过滤器（Filters）。
n   连接件就象是数据流传输的管道（Pipes），将一
    个过滤器的输出传到另一过滤器的输入 。



                           15
管道和过滤器风格




           16
管道和过滤器风格

n   该风格的限制条件：
    n   过滤器必须是独立的实体，它不能与其它的
        过滤器共享状态；
    n   一个过滤器不知道它上游和下游的标识；
    n   一个管道和过滤器网络输出的正确性不应依
        赖于过滤器进行增量计算过程的顺序。




                              17
管道和过滤器风格
n   该风格的特例：
    n   pipelines：将拓扑结构限定为过滤器的线性结构。
    n   bounded pipes：限定了可以存在于一个管道上的数
        据量。
    n   typed pipes：在两个过滤器之间传递的数据具有特定
        的类型。
    n   batch sequential：每个过滤器把它所有的输入作为一
        个单一实体进行处理。
n   应用：
    n   Unix shell：cat file｜grep xyz｜sort｜uniq>out
    n   编译器：词法分析、句法分析、语义分析、代码生成

                                                18
管道和过滤器风格
n   管道和过滤器风格的优点：
    n   使得软构件具有良好的隐蔽性和高内聚、低耦合的特点；
    n   允许设计者将整个系统的输入／输出行为看成是多个过滤
        器的行为的简单合成；
    n   支持软件重用。只要提供适合在两个过滤器之间传送的数
        据，任何两个过滤器都可被连接起来；
    n   易于维护和增强系统。新的过滤器可以添加到现有系统中
        来；旧的可以被改进的过滤器替换掉；
    n   允许对一些如吞吐量、死锁等性质进行分析；
    n   支持并行执行。每个过滤器是作为一个单独的任务完成，
        因此可与其它任务并行执行。
                               19
管道和过滤器风格

n   管道和过滤器风格的缺点：
    n   通常导致进程成为批处理的结构。这是因为虽然过滤器可
        增量地处理数据，但它们是独立的，所以设计者必须将每
        个过滤器看成一个完整的从输入到输出的转换。
    n   不适合处理交互的应用。
    n   过滤器的独立性意味着某些过滤器可能会重复其他过滤器
        执行的预备函数（解析和合成数据的工作），这样就导致
        了系统性能下降，并增加了编写过滤器的复杂性。

数据抽象与面向对象风格


n   将数据的表示和相关操作封装在一个抽象
    数据类型或对象中。
n   这种风格的构件是对象，或者说是抽象数
    据类型的实例。
n   对象是通过方法和过程的调用来交互的。



                     21
数据抽象与面向对象风格




n   该风格的两个限制：
    n   对象要负责保证其数据表示的完整性；
    n   对象的数据表示对其他对象来说是隐藏的。
                              22
数据抽象与面向对象风格


n   面向对象风格的优点：
    n   因为对象对其它对象隐藏它的表示，所以可
        以改变一个对象的表示，而不影响其使用者。
    n   由于访问数据的操作和数据的绑定使得设计
        者可将问题分解成一些交互代理的集合。




                              23
数据抽象与面向对象风格

n   面向对象风格的缺点：
    n   为了使一个对象和另一个对象通过过程调用
        等进行交互，必须知道对象的标识。只要一
        个对象的标识改变了，就必须修改所有其他
        明确调用它的对象。
    n   不同对象的操作关联性弱。例如，如果A使用
        了对象B，C也使用了对象B，那么，C对B的
        使用所造成的对A的影响可能是料想不到的。



                              24
基于事件／隐式调用风格
n   基于事件/隐式调用（Implicit Invocation）
    风格的思想是构件不直接调用一个过程，而
    是发布或广播一个或多个事件。
n   系统中的其它构件为它感兴趣的事件注册过
    程。
n   当一个事件被发布，系统自动调用在这个事
    件中注册的所有过程，这样，一个事件的发
    布就“隐式地”激发了另一模块中的过程。


                                 25
基于事件／隐式调用风格


n   构件：是这样一些模块：它们的接口既提
    供了一些过程，也有一些事件的集合。这
    些过程既可以用一般的方式调用，也可能
    被注册为与某些事件相关。
n   连接件：对过程的显式或隐式调用。

基于事件／隐式调用风格

n   该风格的特点：
    n   事件的发布者并不知道哪些构件会被这些事件影
        响。这样不能假定构件的处理顺序，甚至不知道
        哪些过程会被调用。
n       应用：
    n   在编程环境中用于集成各种工具；
    n   在数据库管理系统中确保数据的一致性约束；
    n   在用户界面中分离数据和表示；
    n   在编辑器中支持语法检查。

                               28
29
基于事件／隐式调用风格

n   隐式调用风格的优点：
    n   为软件重用提供了强大的支持。当需要将一个构件加
        入现存系统中时，只需将它注册到系统的事件中。
    n   为改进系统带来了方便。当用一个构件代替另一个构
        件时，不会影响到其它构件的接口。
n   缺点：
    n   构件放弃了对系统计算的控制。
    n   声明或广播某个事件的过程的语义依赖于被触发事件
        的上下文约束，关于正确性的推理存在问题。

层次系统风格
n   层次系统（Layered System）组织成一个层次结
    构，每一层为上层服务，并作为下层的客户。
n   在一些层次系统中，除了一些精心挑选的用于
    输出的函数外，内部的层只对相邻的外层可见。
n   构成：
    n   构件：各层次内部包含的构件；
    n   连接件：层间交互的协议；
    n   拓扑结构：分层；
    n   拓扑约束：对相邻层间交互的约束。
n   应用例子：分层通信协议、数据库系统、操作
    系统……

                               31
层次系统风格




         32
层次系统风格
n   层次系统风格的优点：
    n   支持基于抽象程度递增的系统设计，使设计者可以把
        一个复杂系统按递增的步骤进行分解；
    n   支持功能增强，因为每一层至多和相邻的上下层交互，
        因此功能的改变最多影响相邻的上下层；
    n   支持重用。只要提供的服务接口定义不变，同一层的
        不同实现可以交换使用。这样，就可以定义一组标准
        的接口，而允许各种不同的实现方法；
    n   对标准化的支持。清晰定义并广泛接受的抽象层次能
        促进实现标准化的任务和接口开发，同样接口的不同
        实现可以互换。

                              33
层次系统风格

n   层次系统风格的缺点：
    n   并不是每个系统都可以很容易地划分为分层的模式，
        甚至即使一个系统的逻辑结构是层次化的，出于对系
        统性能的考虑，系统设计师不得不把一些低级或高级
        的功能综合起来；
    n   效率降低；
    n   如何界定层次间的划分是一个比较复杂的问题。

仓库（Repositories）风格


n   两种不同的构件：
    n   中央数据结构说明当前状态；
    n   一组独立构件对中央数据结构进行操作。
n   连接件：
    n   仓库和独立构件间的交互。




                             35
仓库（Repositories）风格


n   两个主要的子类别：
    n   若是输入事务触发选择执行进程的，并将执
        行结果作为当前状态存储到中央数据结构中，
        则仓库是传统的数据库体系结构；
    n   若是中央数据结构的当前状态触发选择执行
        进程的，则仓库是一黑板系统。




                              36
仓库（Repositories）风格




                     37
仓库（Repositories）风格

n   黑板系统主要由三部分组成：
    n   知识源：待解决的问题被分解成若干个小问题，每个小
        问题由独立知识源负责计算。知识源中包含独立的、与
        应用程序相关的知识，知识源之间不直接进行通讯，它
        们之间的交互只通过黑板来完成。
    n   黑板数据结构：黑板数据是按照与应用程序相关的层次
        来组织的问题求解状态数据，知识源通过不断地改变黑
        板数据来解决问题。
    n   控制器：控制完全由黑板的状态驱动，黑板状态发生改
        变知识源就会响应。


                               38
仓库（Repositories）风格


n   黑板风格举例——语音识别
    n   Hearsay Ⅱ语音识别项目。该系统以自然语言的
        语音信号为输入，经过音节、词汇、句法和语义
        等多个方面的分析，得到用户对数据库的查询请
        求。




                               39
仓库（Repositories）风格

n   优点：
    n   便于多客户共享大量数据，不用关心数据何时
        有的、谁提供的、怎样提供的；
    n   便于添加新的作为知识源代理的应用程序。
n   缺点：
    n   不同的知识源代理对于共享数据结构要达成一
        致，造成对黑板数据结构的修改较为困难；
    n   需要一定的同步/加锁机制保证数据结构的完整
        性和一致性，增大了系统复杂度。

解释器（Interpreters）风格

n   解释器读入伪代码，并将它转化成可以运行
    的实际代码。
n   四种构件：
    n   转换伪代码和模拟它所代表的程序的解释引擎；
    n   包含待解释伪代码的存储器；

n   连接件：过程调用和直接存储器访问

解释器（Interpreters）风格
n       Interpreter takes a string of characters, called pseudocode,
        and converts it into actual code that is then executable.
n       Interpreter can be used not only to convert programming
        language to machine code, but also to convert any kind of
        encoding to a more explicit or usable form.
n       The interpreter is composed of four parts:
    n     A memory to contain the pseudocode to be interpreted;
    n     An interpretation engine to convert the pseudocode and simulate the
          program it represents;
    n     The current state of the interpretation engine;
    n     The current state of the program being simulated.

过程控制风格

n   特点：
    n   过程控制系统不仅是由在设计中出现的构件类型，而且
        由构件之间的关系刻画它的特征。
    n   通过对输入和中间产品的持续的操作而将输入转换为具
        有特定属性的最终产品。
n   目的：
    n   将过程结果的特定属性维持在称为“设定点”的参考值
        附近。(如:核电站/空调)
n   两种类型：
    n   反馈控制、前馈控制

                              47
过程控制风格


n   过程变量：某个过程的可以被测量的属性；
n   受控变量：系统希望控制其值变化的那些过程变
    量；
n   输入变量：用于监测过程的某个输入的过程变量；
n   操作变量： 控制器可改变其值的那些过程变量；
n   设置点（Set point）：受控变量的期望值。



                               48
过程控制风格
n   反馈控制系统
    n   A feedback system measures a controlled
        variable, such as temperature, and adjusts the
        process accordingly to keep the controlled
        variable near or at the set point.
n   前馈控制系统
    n   In feedforward, the system tries to anticipate
        future effects on the controlled variable by
        measuring other process variables that may be
        good indicators.

n 公共数据方案

 n 易于形成解决问题的思路，在初次面对一个（较
  复杂）问题时可先采用此法做一个设计草案；
 n 特点是数据无封装，其表示形式要让各模块都知
  道，数据被各模块直接访问；
 n 问题在于：数据结构的表示可能发生改动，比如
  出于效率的考虑仅用{行号，位移}表示一个循环
  移位的行。数据结构的改变会影响这里的各模块，
  因此这个方案不易改进，更不易重用到其他问题
  的解决中。

n 抽象数据类型方案




                 62
软件体系结构示例——软件设计方案的对比

n 抽象数据类型方案
 n 数据被封装，向外提供访问数据的接口，因此
  数据结构以及与其相关的算法的改变比公共数
  据方案的容易了，重用的可能性也较高。
 n 但抽象数据类型内部仍需要关于其他数据类型
  接口方面的知识，以形成一个数据加工的链条，
  并由主控模块顺序激活这个链条。因此在这种
  方案中添加新功能是较困难或麻烦的 ——这种
  设计是僵硬的。

n 隐式调用方案
 n 数据被封装，且数据内部不包含有关功能方面的知识。

 n 主控模块不包含数据处理链条的中间细节环节（功
  能），只负责数据处理（问题解决）的初始化和终结
  部分。
 n 具体功能（中间环节）独立设计，它们会使用数据，
  它们是靠隐式调用连成一个处理链条，不必在自己内
  部指明下面的流程要转向哪个模块，只需声明自己的
  通知事件，而由下游链条注册这些事件。
 n 因此这种方案易于在未来添加新功能。

n 管道－过滤器方案

软件体系结构示例——软件设计方案的对比

n 管道－过滤器方案
 n 因为没有了共享数据的要求，管道－过滤器方
  案最易于改变和重用过滤器（功能、算法）。
 n 这种方案最能体现和控制数据处理的顺序。

 n 但是由于在过滤器之间传递的类型固定，这种
  方案不易改变数据的表示形式。
 n 这种方案适合批处理，不适合构造交互式数据
  处理系统。
