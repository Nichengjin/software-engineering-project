为何需要软件项目管理？

n 是否需要管理是专业软件开发和业余编程之间的重
 要区别之一：
 n 专业的软件开发活动总是要受预算和工程进度等的制约；
 n 有多方面的参与者需要协调或管理；
 n 软件项目管理者要确保项目符合预算和进度要求，还要
   确保交付的软件能达到既定的目标；
 n 再好的管理也不能保证项目绝对成功，但糟糕的管理常
   常造成项目失败；
项目管理中的基本概念

  什么是项目？
  n 项目是为了创造一种独特的产品、实现一
  种独特的服务或达成一项独特的结果而做
  出的暂时性努力。
项目管理中的基本概念

区分项目和运营：
n 项目（Project）
 n 是暂时性的，具有确定的起止日期；
 n 当项目的目标实现后，项目就算完成了；
 n 有时，如果已经确定项目的目标无法实现，项目也算结束了，
   或说取消了；
n 运营（Operation）
 n 是连续性的，没有起止日期，往往是重复同一工作程序；

n 明确这个区别，注意界定“项目”的含义。
项目管理中的基本概念

项目的特征：
n 项目是独特的；
n 项目是暂时性的，存在明确的起止日期；
n 当目标达到后，项目就算完成了；

n 一个成功的项目需要满足甚至超过项目干系人的
 期望；
项目管理中的基本概念

项目约束：
n 几乎每个项目都是在时间、金钱（资源）和质量的
 三重约束下进行的；
n 项目经理的最主要工作之一就是平衡各种项目约束，
 从而实现或超过项目干系人的期望值；
软件项目中的管理活动

n 软件管理并没有一定的标准，开发组织和被开发的软
  件产品决定着管理工作的内容
n 基本上，软件项目管理工作要包含以下活动：
 n 提出书面建议
 n 项目规划和进度

 n 项目成本估算

 n 项目监督和评审

 n 人员选择和评价

 n 写作并陈述工作报告
软件成本

n 注意：与其他管理活动一样，软件成本估算随着项目的
  进行需要定期修正。
n 软件成本包括：
 n 包括维护在内的硬件和软件费用；

 n 工作成本（支付给软件开发人员的费用）；
 n 应用的方法、过程所形成的一部分成本；

 n 使用的工具；

 n 差旅费；
软件成本

n 计算软件成本还要考虑使开发机构运作的经常性管
 理费用：
 n 办公场所、水、电、供热等费用；

 n 会计、文秘、硬件技师等辅助人员的费用；

 n 网络和通信费用；
 n 资料室、娱乐设施等共用设施的费用；

 n 退休金、医疗保险等社会保障和员工福利费用；

n 对于多数项目，工作量是软件成本最大的一块，并
 且也是最不确定的一块。
软件工作量估算

n 软件工作量估算是预测构造一个软件系统所需的
  总工作量的过程。
n 工作量估算要贯穿整个软件开发过程：
 n 需要用初步估算来确定一个项目的可行性；

 n 需要详细估算来协助制定项目计划；

 n 要将每个任务的实际工作量与计划工作量反复做对比，
 以便项目经理在必要的时候重新分配项目资源；
n 工作量估算从软件规模的估算入手。
软件规模估算的两种方法

n 代码行技术：这种方法依据以往开发类似产品的
 经验和历史数据，估计实现一个功能所需要的源
 程序行数。
n 功能点技术：看交付的软件的总功能有多少。依
 赖对软件信息域特性和软件复杂性的评估结果估
 算软件规模。功能点（FP）和对象点是这种估算
 中常用的指标。

代码行方法存在的问题

n 严重依赖项目所使用的开发语言。对使用不同语言开发相
 同项目的情况，单独比较代码行数值没有意义。
n 不同开发组织可以制定不同的代码行计数标准，所以依据
 代码行指标在组织间类比生产率一般是不可能的。
n 代码行方法主要度量编码阶段的工作量，源程序仅是软件
 配置的一个成分，用它的规模代表整个软件的规模似乎不
 太合理。
n 若采用的编码方法和语言在表达和解决问题方面效率高，
 用这种方法计算的生产率反而会低。
用功能点衡量的软件规模

n 功能点用系统的功能数量来衡量其规模。

n 对系统中以下几类部分计数（信息域特性）：
 n 输入项数（Inp）；

 n 输出项数（Out）；

 n 查询数（Inq）；

 n 主文件数（Maf）；
 n 外部接口数（Inf）；
用功能点衡量的软件规模

n   输入项数：用户向软件输入的项数。这些输入给软件提供面向应用
    的数据。输入不同于查询，后者单独计数，不计入输入项数中。
n   输出项数：软件向用户输出的项数。它们向用户提供面向应用的信
    息，例如，报表和出错信息等。报表内的数据项不单独计数。
n   查询数：查询即是一次联机输入，它导致软件以联机输出方式产生
    某种即时响应，即一对儿“请求－响应” 。
n   主文件数：逻辑主文件（即数据的一个逻辑组合，它可能是大型数
    据库的一部分或是一个独立的文件）的数目。
n   外部接口数：机器可读的全部接口（例如，磁盘或磁带上的数据文
    件）的数量，用这些接口把信息传送给另一个系统。
功能点的复杂度权重




 n   由各项的计数同与其对应的复杂度权重计算加权和，此为未经调
     整的功能点计数（UFP）。
技术复杂度因子（TCF）的组成

  n F1-可靠的备份和恢复   n F8-在线升级

  n F2-数据通信       n F9-复杂界面

  n F3-分布式处理功能    n F10-复杂数据处理

  n F4-性能         n F11-重复使用性

  n F5-大量使用的配置    n F12-安装简便性

  n F6-联机数据输入     n F13-多工作点安装

  n F7-操作简便性      n F14-易于修改
功能点的计算

  n 前面根据计数和复杂度权重得出的加权和是未经
    调整的功能点计数（UFP）；
  n TCF的每一部分取值为0到5，0表示该部分对系统
    没有影响，5表示该部分对系统很重要；
  n TCF = 0.65 + 0.01(SUM(Fi))；

  n TCF的取值在0.65到1.35之间；
  n 最后，功能点计算公式为：FP = UFP × TCF
衡量软件规模的功能点指标

  n 生产率 ＝ FP／PM（人月）

  n 成本 ＝ 元／FP

  n 质量 ＝ 错误数／FP

  n 文档 ＝ 文档页数／FP
根据专家经验来估算软件工作量

n 使用代码行或功能点方法，估算出乐观值a、悲观值b、
  最可能值m；
n 计算期望值S = (a + 4m + b) / 6；

n 使用生产率的历史数据（KLOC/PM、FP/PM），得出
  估算的工作量；
n 这种方法使用的历史数据应注意更新调整，以适应当
 前时期与当前的工作环境。
Delphi技术－专家判定的改进

n 邀请N位专家，在小组会议上讨论项目估算；
n 每位专家得出一个期望值Si，并无记名提交；
n 会议组织者计算S＝SUM(Si) / N；
n 每位专家根据S，可以考虑修改自己的Si，并再
  次无记名提交；
n 重复以上两步骤，直到各位专家不愿再修改自
  己的Si。
专家经验法不足之处

n 依赖主观判断：受专家经验、能力、偏好等不准确
 性影响；
n 按比例是不可靠的：项目成本不总是线性的。“两
 个人的效率不是一个人的两倍”；
n 过于简化：忽略了能影响工作量的大量因素，如产
 品性能、人员素质、项目特殊要求等方面。

     使用经验估算模型估算软件工作量

     n   估算模型是利用从过去的软件项目收集得到的数据
         进行统计分析而导出的。
     n   软件规模通常是估算模型的主要因素，由它得出初
         步估计后，再根据许多次要调节因素进行调整。
     n   估算模型种类：
         u   静态单变量模型
         u   动态多变量模型（考虑了时间的因素）

     COCOMO模型

     n   COCOMO模型把软件项目从总体上分成三种类型：组织
         型、半独立型、嵌入型：
         u   组织型：相对简单的项目，需求不算严格，开发人员对此
             问题经验丰富，受硬件约束少，规模小于5万行。如简单
             的商业数据处理系统；
         u   半独立型：中等规模的项目，正式与非正式的需求混杂。
             如大型库存与生产控制系统；
         u   嵌入型：必须在严格的硬件、软件、操作约束下进行的项
             目。如飞机的飞行控制软件。

     COCOMO II模型

     n   应用系统组成模型：
         u   使用对象点（OP）来度量规模；
         u   首先确定原型的屏幕数、报表数、三代语言构件数；
         u   确定上述3种对象的复杂度；
         u   由复杂度权重算得加权对象点数；
         u   根据复用比例r算得新对象点数NOP；
         u   算得生产率PROD，再算得估算工作量。

         估算软件工作量的几个基本原则

     n   尽可能采用分解问题的策略来进行估算：
         u   自顶向下：从系统级开始
         u   自底向上：从组件级开始
         u   差别估计法：综合上述两种方法的优点，根据相似性进行估算。
     n   不要只依赖一种估算方法，应使用多种方法进行估算并
         做交叉检验。
     n   估计方法与数据收集要一致。
