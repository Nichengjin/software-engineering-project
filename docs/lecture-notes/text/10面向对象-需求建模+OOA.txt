Use Case
 n Use Case的引出

  n 了解需求→分析典型用例→ 不自觉、随意、潦
    草→ Jacobson提出Use Case分析法→ OO技术
    进入第二代；
 n Use Case是什么

  n 本质上，一个Use Case是用户与计算机之间为
    达到某个目的的一次典型交互作用；
  n 作为结果，Use Case代表的是系统的一个完整
    功能。

Use Case

 n Actor：

   n Actor是与系统交互的外部实体；

   n Actor是具有构造型《Actor》的类，所以谈论
    Actor时考虑的是其角色，而非角色的实例；
   n Use Case总是由Actor启动的；

   n Actor与Use Case间是多对多的关系。

  n Actor有助于获取Use Case

   n 先找出各Actor，再通过他们得到Use Case。

  n 处理Actor与Use Case的关系

   n 一般不必过分关注Actor的细节；

   n 若需对系统分析优化，应了解Actor细节；

   n 对每个用户，提供一张Actor列表，指明其

     有助于协调需求冲突、制定安全策略。

n 用户目标（user goal），它是主参与者努力使工作
 得以完成的目标，或是用户使用系统的目标，相当
 于业务过程中的“基本业务过程”。
 n “这个操作执行完以后，主参与者会高兴地离开吗？”

 n “做完这件事之后，我能获得工间休息？”

 n 多数情况下，用户目标应通过“一人、一次处理完成”
  测试（2~20分钟）
n 用户目标是需要被编写的重要目标，系统的价值体
 现在其对用户目标的支持上。
概要层次（白色，云朵               ， 风筝     ）

n 概要层次目标（summary-level   goal）包含多个用
 户目标，其有三方面的功能：
 n 显示用户目标运行的语境

 n 显示相关目标的生命周期顺序

 n 为低层用例（包括白色用例和蓝色用例）提供一个目
   录表
n 概要用例通常要执行几个小时、几天、几个星期、
 几个月、甚至几年。

n Use Case间的关系：包含、扩展、泛化
 n 包含：两个Use Case，如果其中一个在其事件流中包
  含了另一个，那么它们间就有包含关系。
 n 扩展：将常规动作放在一个基本Use Case中，将非常
  规动作放在其扩展Use Case中。
 n 泛化：对一般性Use Case做特殊化、细化。

Use Case
 n Use Case的获取分两步：

 n 要获取Actor，请对用户／客户提问：

  n 谁使用系统的主要功能（Primary Actor）？

  n 谁需要系统支持他们的日常工作？

  n 谁来维护、管理系统（Secondary Actor）？

  n 系统需要控制哪些硬件？

  n 系统需要与其他哪些系统交互？

  n 对系统产生的结果感兴趣的是哪些人或事物？

确定参与对象

n 确定每个Use Case的参与对象；

n 参与对象对应于问题空间的主要概念→形
 成术语表；
n 参与对象的确定产生了最初的分析模型：

 n 对象的描述、属性可由用户评审；

 n 作为整个分析模型与用户／客户衔接的部分，
  通常不会用完整的分析模型“烦恼”用户。



                        29
确定参与对象的试探法

n   开发人员或用户为理解Use Case所必须阐明的术语；
n   Use Case中的常用名词（如，事件）；
n   系统需要跟踪的现实世界实体（如，现场工作人员、资
    源）；
n   系统需要跟踪的现实世界过程（如，紧急操作计划）；
n   Use Case本身（如，报告紧急情况）；
n   数据来源或数据接受器（如，打印机）；
n   接口产品（如，工作站）；
n   总要使用的应用域的术语。

从需求提取到分析

n 需求提取→Use Case和场景形式的需求说
 明→细化描述、规范和形式化→形成分析
 模型。
n 分析模型要：准确、完整、一致、可检验。
 它其实对应着传统的需求规约文档，但同
 时它也包含系统高层设计的起始部分。



                           34
分析概述
n 分析模型包括：

 n 功能模型：Use Case图表示

 n 对象模型：类图、对象图表示

 n 动态模型：顺序图、状态机图表示

n 分析活动：

 n 也称为“用例分析”，即针对用例模型中的每
  一个用例
  n 提取“分析类”

  n 转述Use Case或场景

  n 整理“分析类”

“分析类”的含义


n “分析类”是概念层的内容，从它们可捕获
 系统对象模型的雏形；
n “分析类”相当粗略，不要往其中添加技
 术细节。




                    36
“分析类”的划分

n 划分原则：要尽量减小需求变化的影响—
 —“高内聚、低耦合”。
n 实体类：系统要记录和维护的信息；

n 边界类：系统和外部要素间交互的边界；

n 控制类：Use Case中行为的协调；

 n <<entity>>、<<boundary>>、<<control>>；

                   39
实体类的含义



n 实体类描述必须存储的信息，以及与这些
 信息直接相关的操作；
n 实体类与系统外部环境以及特定Use Case
 的控制逻辑要弱耦合。




                           40
边界类的含义

n 边界类描述系统外部环境与内部运作之间
 的交互；
n 主要负责内容的翻译、形式的转换，并表
 达相应结果；
n 边界类把系统其他部分（实体类、控制类）
 与外部环境隔离；
n 注意这是概念层，不是要做具体界面。



                      41
控制类的含义

n 控制类描述一个 Use
           Case 特有的事件流中
 的控制行为，起协调人作用；
n 控制类把 Use
       Case 特有的行为与系统其他
 部分（实体类、边界类）隔离开来；
n 实体类和边界类有可能跨越多个 Use   Case 。

n 边界类：通常一个 Actor 与 Use   Case之间的

n 控制类：通常一个 Use   Case 对应一个控制

识别边界对象的试探法

n 确定用户需要将数据输入系统的窗口或表格（如，
 紧急情况报告表单，报告紧急情况按钮）；
n 确定系统对用户的响应或消息（如，确认通知）；

n 不要用边界对象对界面的可视方面建模（用户模型
 更适于做这件事）；
n 使用用户的术语而不是实现技术的术语来描述界面。

n 这种过程一般需要选择某种辅助建模工具软件

检查分析模型
n 分析模型用渐进循环方式构建。在第一次构建中，
 分析模型很少是正确的，甚至是不完整的；
n 在分析模型形成一个正确的说明、从而能被用来
 进行后面的设计和实现之前，与客户和用户间的
 多次循环是必要的；
n 一旦分析模型变得稳定，应该首先由开发人员检
 查它，然后是开发方与客户的联合检查。检查针
 对的目标就是确保需求说明的几种特性：正确性、
 完整性、一致性、可测试性、现实性等。

                       86
分析阶段的注意事项
n 标识实体对象时，要考虑到分析模型处于
 不断变化中，不必花费太多时间来处理对
 象或其属性的细节。如果它们是显而易见
 的，应该记录下来，否则，对每个对象进
 行试验性的命名和简短描述即可。然而，
 一旦分析模型稳定下来，每个对象的描述
 就应该尽可能详细。



                   87
分析阶段的注意事项
n 标识边界对象时，是对用户界面的粗略建
 模，它并不详细描述用户界面的可见方面，
 那些工作应放在用户模型去做。用户界面
 的设计将不断演化，甚至在系统的功能性
 说明稳定下来以后仍会变。如果分析模型
 和界面的可视部分的变动互相影响，将耗
 费很多时间在它们间做协调。



                   88
分析阶段的注意事项
n 控制对象通常在现实世界没有具体的对应
 部分。控制对象通常在一个用例的开始被
 创建，当用例终止时它就不复存在。若很
 难确定一个控制对象活动的开始和结束，
 则表明对应的用例可能没有一个定义明确
 的入口和出口条件。




                   89
分析阶段的注意事项

n 实体类与属性的差异：
 n 类的属性和独立的实体类有所不同。但界限并不十分清
  晰。在以下两种情况下，通常将特定客体（信息）建模
  为独立的实体类：
  n 客体具有比较复杂的自身行为；

  n 客体具有独立标识（ Identification ），有可能被多类对象
   共享或传递。
 n 在以下情形，通常将特定客体建模为类的属性：

  n 客体只有非常简单的取／赋值操作（ set ， get 等），无更
   多其他行为；
  n 客体不需要独立标识，仅供一类对象使用。


                                      90
分析阶段的注意事项
n 有些时候，建模形式的选择不容易一步到位。

 例如，在分析和设计的演进过程中，如果发现
 之前定义的实体类 A 几乎没有行为并且仅仅被
 另外一个类B使用，那么可以将类A转换成类B
 的一项属性 a 。相反地，如果类 X 的某个属性 y
 越来越显现出复杂的行为特征，则可以考虑将
 该属性建模为一个独立的实体类Y。




                              91
分析阶段的注意事项
n 当模型逐渐清晰时，应检查各“分析类”
 间的关系：
 n 把一对多、多对多的复杂关系尽量变为受限的
  一对一关系；
 n 把“分析类”体现的概念组成层次，即从特殊
  到一般的“归纳”，即泛化。
n 这些是试图减少关系的数量、降低复杂性
 的手段，但是要注意：


                      92
分析阶段的注意事项
 n 泛化（generalization）不等同于继承；

 n 继承是一种复用（即重用）属性和行为的机
  制，即使继承的类之间不存在归纳关系，比
  如，把散列表类改进成集合类的这种“继
  承”；
 n 在分析中仅仅关注把概念组织成泛化关系，
  而不能用复用的形式来解释。继承层次结构
  将在对象设计中重新构建。

分析总结

 n 检查模型的阶段当然也存在修改用例的可能性；
